长连接与加密

长连接与加密

实时下发的全部机制：一条 WebSocket、一次握手、之后所有帧都进同一个加密通道。这一页解释为什么每个环节长这样——照抄形状容易，抄错语义就会得到"消息偶尔不来"。

端点

WS   wss://{host}/ws?since_seq={lastSeq}

  • since_seq 是这条连接唯一的 query 参数，客户端存的水位号。缺省视为 0（全量补拉）。
  • token 不在 URL 里，它在 auth 帧里。URL 会落进访问日志与反向代理日志，凭据进去就等于泄露。
  • 握手之前只有一个明文帧：hello。握手之后下行一律 {t:"enc",n,data}。

握手时序

#方向帧明文?内容与作用
1下行hello是server_time · heartbeat（秒） · server_pub_fp · nonce（32 字节 base64，这是客户端签名的挑战值）
2上行auth是device_id · token · ts · sig
3下行kx是server_pub · eph_pub · sig · epoch
4下行enc…否补拉的历史帧 + resume_ok，之后是实时消息

服务端从不发 auth_ok

authenticate() 验签通过后直接回 kx。所以"kx 到了"才是握手成功的信号；把"等一个 auth_ok"当成就绪条件，会得到一条永远不建通道的连接。auth_ok 这个类型留在帧表里只为兼容第三方实现发出它——Android 客户端收到它是 Unit（忽略）。失败才有下行：auth_fail 带 error（expected_auth / invalid_device / clock_skew / bad_signature），发完即按 policy violation 关闭。

服务端如何确认"你真的持有私钥"

握手帧的 canonical 是四行，逐字节：

pushbox-ws-auth-v1
{deviceId}
{base64(serverNonce)}          # hello 里那枚 32 字节挑战值
{ts}                            # epoch 毫秒，窗口 ±300s

用设备的 sign_pubkey（注册时上传的那把）验 Ed25519。token 只是"找设备"的索引，能不能连由签名决定：token 泄露但私钥没走，攻击者仍然连不上；私钥泄露则 token 也拦不住。

TOFU：怎么确认对端是"你的"服务端

客户端手里没有服务端的指纹就无从验签，所以 kx 同时带身份公钥，客户端按两步走：

  1. 比对 sha256(server_pub) 前 16 位与本机已固定的指纹。首连即固定（TOFU）；之后再变就该拒绝，而不是"弹个框问一下"。
  2. 用这把身份公钥验 kx.sig，签名覆盖的字节是 server_eph_pub ‖ nonce（直接拼接，不是先哈希）。

换正式证书后指纹必然变，这是预期行为——客户端要能"换绑"，Android 的重启/清数据、Windows 的换 CA 都会重记指纹。别把它实现成"永久锁死"。

密钥层级

材料算法谁持有用途
设备 enc 密钥对X25519私钥只在设备，公钥上传下行会话密钥 K 的协商、REST 响应密封盒
设备 sign 密钥对Ed25519私钥只在设备，公钥上传WS 握手签名、REST 请求签名
服务端身份密钥对Ed25519服务端进程签 kx；指纹 server_pub_fp 供 TOFU
会话密钥 KX25519 → HKDF-SHA256每条连接各算一次帧的 AES-256-GCM 密钥；info 串 pushbox-frame-v1
恢复码服务端只存哈希用户抄写换机/加设备。丢了没有找回途径

派生：共享点 shared = X25519(deviceEph.priv, deviceEnc.pub)，再 K = HKDF(shared, salt=nonce)——WS 用 hello 的 nonce 作 salt，REST 密封盒用 sha256(eph_pub) 作 salt。帧加密是 AES-256-GCM，nonce = 帧序号 n，AAD = n，所以序号重复必然解密失败，重放无处藏。

帧类型表

一行一个 JSON 帧。解析到未知 t 必须忽略而不是崩溃——这是协议能向后加帧的唯一前提。

t方向载荷要点语义
hello↓ 明文见握手连接即发
auth / kx / auth_fail↑ / ↓ / ↓ 明文见握手握手三帧
enc↓ 密文{t,n,data}，data=base64(AES-GCM)唯一的密文载体，解开后里面才是下面这些帧
message↓seq id channel_no sender_id type title summary content level url media[] sender_name sender_avatar created_at notify truncated一条新消息。到达客户端时 media[] 通常已是终态（合并窗口的作用），收到即可直接带图发通知
media_ready↓id seq media[] status兜底帧：不带新 seq，客户端按 id 原地补图，不重复通知、不推进已读游标
media_failed↓结构同上，只是 t 不同重试耗尽后仍失败。客户端把对应格子画成「已失效」，不要再等

组内广播：一条消息，N 份信封

消息落库一次（全局 seq），下发则是逐连接的：服务端遍历会话表里 group_id 相同的每一条 session，各自持锁、用该连接自己的会话密钥与帧序号封一个 enc 信封再写出去。所以同一秒里两台设备收到的是同一条明文、互不相干的密文——帧序号与 nonce 按连接独立，一条连接的 ratchet 不影响另一条。

  • 会话表按 device_id 唯一：同一个设备身份的新连接进来会主动关掉旧的那条，不等心跳超时。这一条决定了"两台设备都收到"必须是两个 device_id；把一端的身份复制到另一台机器，得到的只是"两台轮流持有同一条连接"，症状是只有一端收得到而且随启动顺序漂移。
  • 带频道内容的帧要过逐设备的订阅过滤器：下发前先一次 SQL 取出"这组里哪些设备能收这条频道"（subscribed_only=0，或已接入这条）；config、read 这类不带内容的控制帧永远全组广播、不过滤。这也是接入与取消接入不发 config 帧的原因之一（见下表）。
  • 写失败就摘掉那条会话，继续下一个设备：一个已经死掉的客户端不会把整组广播卡住，剩下的那台照样收到。
  • 日志里那句 在线下发=N 是这个循环发出去的连接数。两端都在线时它应该是 2——"为什么只有一端收到"，第一站就看这个数字。

补拉：断线之后会发生什么

验签通过、通道建好后，服务端立刻按连接上的 since_seq 补发：

latest = 本组最大 seq               # 不是全局 MAX(seq)，见下面第二条
if (latest - since_seq > 2000)      -> 发 resume_gap，到此为止，客户端走 REST
else
  cursor = since_seq
  loop:                               # 每批 pb.ws.replay-batch（默认 500）
    rows = 取 cursor 之后的消息（本 Space，且过一遍订阅过滤器）
    if rows 为空: break
    逐条发 message 帧（notify=false，走同一个截断规则）
    cursor = 最后一条的 seq
  发 resume_ok                        # 整个循环跑完才有这一帧
  • resume_ok 是唯一"已追平"标记，整个循环跑完才发一条。补拉帧一律 notify=false——已有同样内容不该重复弹通知。
  • 落后超过 2000 条时不发逐条重放，改回 resume_gap{missing_from, latest_seq}，让客户端走 REST 分页拉。"重放快"不等于"重放合适"：几千条帧挤在一条刚建好的连接上，既占带宽又把首屏堵死。这里的 latest 只能跟自己组的行高比：seq 是全局单调的，拿全局 MAX(seq) 减一个刚建好、一条消息都没有的 Space，游标恒为 0，别的 Space 推够 2000 条就把它永远顶过阈值——每次连接都只回 resume_gap、等不到 resume_ok，客户端顶栏停在"连接中"而那条连接活得好好的（真服务体检 ② 抓到）。REST 那侧的 latest_seq 仍是全局值，因为 after_seq 本来就是全局游标。
  • 这里有个真实踩过的坑：早先的实现只发一批。落后条数落在"一批"与 2000 之间的设备既收不满、也收不到 resume_gap，客户端把"这批发完"当成"已经追平"，剩下的消息要等下次断线重连才有机会补上——不重连就永久静默。现在补拉是循环到取空，并由验收探针 ㉑ 用"501 条落后"这一档把回归锁住。
  • 发送失败（对端已断）就中断循环，剩下的等它下次重连。
  • 这一圈取出来的消息要过一遍逐设备的订阅过滤器：那台设备开着「只接收已接入的频道」、而这条频道它没接入，就不发。实时下发、WS 补拉、REST 历史、搜索这四条路共用同一个判定，所以不会出现"历史上拉得到、实时收不到"这种自相矛盾；它只是投递过滤，不是权限边界（subscribed_only 默认关，见使用说明）。

心跳与判死

  • hello 里的 heartbeat 就是节奏（pb.ws.heartbeat-sec，默认 25s）：服务端巡检（每 10s 一轮）发现某条连接超过 25s 没有上行，就发 ping；客户端应当回 pong。
  • 超过 heartbeat + 15s（默认 40s）仍无任何上行，服务端直接关闭连接，原因 heartbeat_timeout。
  • 这条线也解释了移动端为什么需要前台服务：系统冻结后台 → 无法回 pong → 服务端判死，重连之后才能补拉。所以 Android 的「后台常驻」不是锦上添花，见使用说明。

重连退避（两端一致）

1s 起指数翻倍、封顶 60s；但如果这次连接活过了 2 × 当前退避，退避就重置回 1s。少了这条，一次长时间掉线会把之后所有重连都拖到 60s 节奏上。

单帧截断

单帧上限 pb.ws.frame-max-bytes（默认 32768 字节）。正文超出时不是整条丢掉，也不是一刀切字节：

  • 按 content_code_points 的码点裁剪（不是 UTF-16 码元），所以永远截不出半个汉字，也修掉了代理对越界的异常；
  • 超出的部分写进 content_truncated_at，帧里 truncated: true；
  • 客户端要全文时按 id 取：GET /api/v1/messages/{id}（对话页的「展开全文」就是这个）。

实时下发与断线补拉走同一个裁剪规则——否则同一条消息"在线收到"和"重连补到"长度不一致，客户端缓存会打架。

这个开关不存在，是有意的

削正文是字节驱动、永远开着的：关掉它等于允许无界大帧。要拿全文走接口，不要走"把帧开大"。

config 帧：让在线的那一端即刻知道

config 帧不带 seq，所以断线期间的这类帧会丢。这是可接受的：客户端每次建连都会重新拉频道面，config 只负责"在线的这一刻即刻知道"，不承担可靠性。

反过来说，接入与取消接入不发 config 帧：它只改这台设备的订阅集，别的设备既不需要知道、也不该因此改变自己的收件范围——所以那两发的结果只回给发起方自己（见客户端 API的频道面）。

reason附带客户端该做什么
secret_rotatedchannel_no提示"旧密钥已作废"（新 secret 不会再下发到别的端）
channel_updatedchannel_no重拉频道面（治理位变了）
channel_archivedchannel_no标记归档态
channel_no_resetchannel_no（新号）本地会话仍以旧号存着，收到这条只需重拉频道面把新号显示出来

channel_no 与 device_id 都可能为 null（组级变更两者都空）。按"整面刷新"处理最省事，也最不容易漏。

密钥轮换

  • 触发条件（任一）：连接跨 24 小时，或本 epoch 已发 2³² 帧。前者是常态，后者防的是"长连接跨年"算崩 AES-GCM 计数器。
  • 做法：拿设备静态 enc 公钥重做一次 X25519，明文下发新 kx（epoch 递增、签名覆盖 eph_pub‖nonce），之后继续走原 since_seq 语义。
  • GCM 单密钥有安全帧数上限，2³² 这个数是照着上限留了大余量挑的。

序号还能当完整性检查用：客户端发现 n 不连续（跳号或回退）就该断开重连带 since_seq，而不是试图"补一帧"——那意味着连接被复用或有人在重放。

实现清单

必须做的

① 首连固定指纹、之后比对；② n 严格递增否则断连；③ 未知 t 忽略；④ notify=false 的补拉帧不出通知；⑤ read 游标只增不减；⑥ 收到 resume_ok 才认为追平；⑦ 重连带 since_seq；⑧ 退避要能重置

容易多做的

① 等 auth_ok（服务端不发）；② 把 media_ready 当新消息再通知一次；③ 收到 resume_gap 还在等重放；④ 对 truncated 帧直接显示省略号而不回捞；⑤ 把 config 帧当可靠通道（它不带 seq）

离线期间的可靠性另有两条兜底：Android 的 WorkManager 约每 15 分钟跑一次 REST 补拉（也是"极致省电轮询"那档），Windows 的删除/已读上报有自己的攒批与退避队列（DeleteReporter，故意只放内存，不承诺跨进程重启不丢）。

联调时怎么看

# 连接数 / 各 Space 水位：判断"是没发还是没收到"的第一现场
PB_TOKEN=<设备令牌> bash deploy/run-dev.sh metrics

# 服务端日志按设备过滤（正文与凭据不会出现在日志里，见服务端 README 的日志节）
grep -F "<deviceId>" ~/Library/Logs/pushbox/server.log      # 本机在 C:\Users\<name>\logs\pushbox\server.log

# 补拉行为：把批次调到很小，观察是否循环发完才回一个 resume_ok
--pb.ws.replay-batch=200

探针 ㉑ 覆盖的正是"落后 501 条 → 逐条收满 → 末尾恰好一个 resume_ok"这条判据；改补拉逻辑一定要跑它。
