长连接与加密

长连接与加密

实时下发只有一条 WebSocket：一条 /ws，一次握手，之后所有帧走同一个加密通道。排查「消息偶尔不来」或对账协议时，参数与帧形状都在这一页。

端点

WS wss://{host}/ws?since_seq={lastSeq}

  • since_seq 是唯一的 query 参数，客户端存的水位号；缺省视为 0，触发全量补拉。
  • token 不进 URL：URL 会落进访问日志与反向代理日志。凭据只写在 auth 帧里。
  • 握手完成前只有 hello 一帧明文；之后下行一律 {t:"enc",n,data}。

连接参数

参数默认值说明
心跳节奏（pb.ws.heartbeat-sec）25shello 里的 heartbeat 就是这个值
判死线40sheartbeat + 15s 内无任何上行即关闭，原因 heartbeat_timeout
重连退避1s → 60s指数翻倍封顶 60s；活过 2× 当前退避后重置回 1s
补拉批次（pb.ws.replay-batch）500循环补发，每批这么多条
补拉窗口2000 条落后超过它就改走 REST 全量补拉
单帧上限（pb.ws.frame-max-bytes）32768 字节超出按码点裁剪正文，不整条丢
签名时间窗±300sauth.ts 与服务端时间的允许偏差

握手时序

#方向帧明文?字段
1下行hello是server_time · heartbeat · server_pub_fp · nonce
2上行auth是device_id · token · ts · sig
3下行kx是server_pub · eph_pub · sig · epoch
4下行enc…否补拉的历史帧 + resume_ok，之后是实时消息

服务端从不发 auth_ok

验签通过后直接回 kx——「kx 到了」才是握手成功。把「等一个 auth_ok」当就绪条件，会得到一条永远不建通道的连接。

失败才有 auth_fail，带 error：发完即关闭连接。

  • hello.nonce：32 字节 base64，这是客户端签名的挑战值。
  • auth.ts：epoch 毫秒，窗口 ±300s。
  • auth_fail.error 取值：expected_auth / invalid_device / clock_skew / bad_signature。
  • auth_ok 这个类型留在帧表里只为兼容第三方实现；Android 收到它直接忽略。

握手帧的形状

{"t":"hello","server_time":1730000000000,"heartbeat":25,"server_pub_fp":"<sha256(server_pub) 前 16 位>","nonce":"<32 字节 base64>"}
{"t":"auth","device_id":"<设备身份>","token":"<设备令牌>","ts":1730000000000,"sig":"<Ed25519 签名>"}
{"t":"kx","server_pub":"<服务端身份公钥>","eph_pub":"<服务端临时 X25519 公钥>","sig":"<Ed25519 签名>","epoch":"<递增整数，轮换时 +1>"}
{"t":"enc","n":"<帧序号>","data":"<base64(AES-256-GCM(内层帧))>"}

sig 用注册时上传的 sign_pubkey 验 Ed25519。token 只是「找设备」的索引，能不能连由签名决定：token 泄露但私钥没走，攻击者仍然连不上。

TOFU：怎么确认对端是「你的」服务端

  1. 比对 sha256(server_pub) 前 16 位与本机已固定的指纹。首连即固定（TOFU）；之后再变就该拒绝，而不是「弹个框问一下」。
  2. 用这把身份公钥验 kx.sig。

换正式证书后指纹必然变，这是预期行为：客户端要支持「换绑」（清数据、换 CA 都会重记指纹），别实现成永久锁死。

密钥层级

材料算法谁持有用途
设备 enc 密钥对X25519私钥只在设备，公钥上传协商每条连接的会话密钥 K；REST 密封盒
设备 sign 密钥对Ed25519私钥只在设备，公钥上传WS 握手签名、REST 请求签名
服务端身份密钥对Ed25519服务端进程签 kx；指纹供 TOFU
会话密钥 KX25519 → HKDF-SHA256每条连接各算一次该连接帧的 AES-256-GCM 密钥
恢复码服务端只存哈希用户抄写换机 / 加设备。丢了没有找回途径
  • 每一台设备、每一条连接都协商自己的会话钥 K。同一秒两台设备收到的是同一条明文、互不相干的密文。
  • K = HKDF(X25519 共享点, salt=nonce)：WS 用 hello 的 nonce 作 salt；REST 密封盒用 sha256(eph_pub)。info 串为 pushbox-frame-v1。
  • 帧加密是 AES-256-GCM，nonce = 帧序号 n，AAD = n：序号重复必然解密失败，重放无处藏。

要自研客户端：逐字节构造、签名规范与测试向量都在 docs/ 里的方案文档，以那份为准。

帧类型表

一行一个 JSON 帧。解析到未知 t 必须忽略而不是崩溃——这是协议能向后加帧的唯一前提。

t方向载荷要点语义
hello↓ 明文见握手连接即发
auth / kx / auth_fail↑ / ↓ / ↓ 明文见握手握手三帧
enc↓ 密文{t,n,data}唯一的密文载体
message↓字段清单见表下一条新消息
media_ready↓id seq media[] status补图兜底
media_failed↓同 media_ready抓取失败的终态
read↓channel_no sender_id last_read_seq device_id某个其他端置了已读
tombstone↓id 或 scope删除同步
config↓reason channel_no? device_id?变更通知，见下表
ping / pong↓ / ↑只有 t保活
resume_ok↓只有 t「已追平」的唯一标记，见补拉
resume_gap↓missing_from latest_seq落后太多，改走 REST
  • enc.data 是 base64 的 AES-GCM 密文；解开后里面才是上面这些内层帧。
  • message 载荷字段：seq id channel_no sender_id type title summary content level url media[] sender_name sender_avatar created_at notify truncated。到达客户端时 media[] 通常已是终态，收到即可带图发通知。
  • media_ready 不带新 seq：按 id 原地补图，不重复通知、不推进已读游标。
  • media_failed：重试耗尽仍失败。对应格子画成「已失效」，不要再等。
  • read 带来源 device_id：客户端应忽略自己发起的那一条。
  • tombstone 的 id 与 scope{channel_no, sender_id} 互斥，先看 id。scope.sender_id 为 null 表示清该频道下所有会话。
  • 服务端不会回 pong：客户端把收到的 ping 当 RTT 样本用。

组内广播：一条消息，N 份信封

消息落库一次，用全局 seq 排序。下发则是逐连接的：每条在线连接用自己的会话钥与帧序号封一个 enc 信封。

  • 会话表按 device_id 唯一：同一身份的新连接会主动关掉旧连接，不等心跳超时。
  • 「两台设备都收到」必须是两个不同的 device_id。把一端的身份文件拷到另一台，症状是只有一端收得到、随启动顺序漂移、全程不报错。
  • 带频道内容的帧要过逐设备的订阅过滤器；config、read 这类不带内容的控制帧永远全组广播、不过滤。
  • 某个设备写失败只摘掉那条会话，继续下一个设备：一台死掉的客户端不会卡住整组广播。
  • 服务端日志里的 在线下发=N 就是本轮广播的连接数。两端都在线时它应该是 2——「为什么只有一端收到」先看这个数字。

补拉：断线之后会发生什么

验签通过、通道建好后，服务端立刻按连接上的 since_seq 补发。

  • 每批 pb.ws.replay-batch（默认 500）条，循环发到取空为止；整个循环跑完才发一条 resume_ok。
  • 补拉帧一律 notify=false：已有同样内容不该重复弹通知。
  • 落后超过 2000 条时不发逐条重放，改回 resume_gap{missing_from, latest_seq}，客户端走 REST 分页拉。
  • 这个阈值里的 latest 是本 Space 的最大 seq，不是全局 MAX(seq)：seq 全局单调，别的 Space 的量不该把新建的 Space 顶过阈值、永远只回 resume_gap。
  • REST 那侧的 latest_seq 仍是全局值，因为 after_seq 本来就是全局游标。
  • 发送失败（对端已断）就中断循环，剩下的等下次重连。
  • 补拉与实时下发、REST 历史、搜索共用同一个订阅过滤器，不会出现「历史上拉得到、实时收不到」。subscribed_only 默认关，见 使用说明。

心跳、判死与重连

  • 服务端巡检每 10s 一轮：某条连接超过 25s 没有上行就发 ping，客户端应当回 pong。
  • 超过 heartbeat + 15s（默认 40s）仍无任何上行，服务端直接关闭连接，原因 heartbeat_timeout。
  • 重连退避（两端一致）：1s 起指数翻倍、封顶 60s；本次连接活过 2 × 当前退避，退避重置回 1s。少了这条，一次长时间掉线会把之后所有重连都拖到 60s 节奏上。
  • 系统冻结后台 → 回不了 pong → 被判死，重连之后才能补拉。所以 Android 的「后台常驻」不是锦上添花，见 使用说明。

单帧截断

单帧上限 pb.ws.frame-max-bytes（默认 32768 字节）。正文超出时不整条丢掉，也不按字节一刀切。

  • 按码点裁剪（不是 UTF-16 码元），永远截不出半个汉字。
  • 超出的部分写进 content_truncated_at，帧里 truncated: true。
  • 要全文就按 id 取：GET /api/v1/messages/{id}（对话页的「展开全文」就是这个）。
  • 实时下发与断线补拉走同一个裁剪规则：同一条消息「在线收到」和「重连补到」内容一致。

config 帧：让在线的那一端即刻知道

config 帧不带 seq，断线期间的这类帧会丢，这是可接受的：客户端每次建连都会重新拉频道面。接入与取消接入也不发 config，结果只回给发起方（见 客户端 API）。

reason附带客户端该做什么
secret_rotatedchannel_no提示「旧密钥已作废」
channel_updatedchannel_no重拉频道面
channel_archivedchannel_no标记归档态
channel_no_resetchannel_no（新号）重拉频道面把新号显示出来
senders_updatedchannel_no重拉白名单
recovery_code_rotated—停掉旧码的展示
device_revokeddevice_id设备名单即刻对上

channel_no 与 device_id 都可能为 null（组级变更两者都空）。按「整面刷新」处理最省事，也最不容易漏。

密钥轮换

  • 触发条件（任一）：连接跨 24 小时，或本 epoch 已发 2³² 帧。
  • 做法：拿设备静态 enc 公钥重做一次 X25519，明文下发新 kx（epoch 递增），之后继续走原 since_seq 语义。
  • 客户端发现 n 不连续（跳号或回退）就断开重连带 since_seq，不要试图「补一帧」——那意味着连接被复用或有人在重放。

实现清单

必须做的

① 首连固定指纹、之后比对；② n 严格递增否则断连；③ 未知 t 忽略；④ notify=false 的补拉帧不出通知；⑤ read 游标只增不减；⑥ 收到 resume_ok 才认为追平；⑦ 重连带 since_seq；⑧ 退避要能重置。

容易多做的

① 等 auth_ok（服务端不发）；② 把 media_ready 当新消息再通知一次；③ 收到 resume_gap 还在等重放；④ 对 truncated 帧直接显示省略号而不回捞；⑤ 把 config 帧当可靠通道（它不带 seq）。

离线兜底：Android 的 WorkManager 约每 15 分钟走一次 REST 补拉（省电/轮询档）；Windows 只有退避重连这一条路，已读与删除上报走内存态攒批队列，不承诺跨进程重启不丢。
