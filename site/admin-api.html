管理台 API

管理台 API

这一组接口是自带 Web 控制台（web-admin/，Vue SPA）的后端契约，也是运维脚本唯一该用的口子。它同时是全库读写权限：跨 Space、能建频道、能吊销设备、能定时灌消息。请把它当运维口对待，不要当业务口用。

选哪个口

给第三方系统发通知 → 入站 API 的 POST /message（一条 curl，凭据只有频道号+密钥，看不到别人的数据）。
自己做客户端（Android / Windows / 自研）→ 客户端 API（设备 token + Ed25519 签名 + 密封盒，只能看自己 Space）。
只有"管这台服务端"——列所有频道、搜所有消息、建定时任务——才是本页。

鉴权：一条口令换一个 24 小时的 JWT

与客户端 API 完全不同的两套机制：管理台不需要 X-PB-Device/Ts/Nonce/Sig 四个签名头，响应也不加密（明文 JSON，没有 sealed box）。代价是它没有任何"只读单个 Space"的余地——token 一验过，权限就是全局的。

POST   {base}/api/v1/admin/login  →  {"ok":true,"token":"<JWT>","expires_in":86400}

项实际行为
请求体{"secret":"<PB_ADMIN_SECRET>"}。字段名是 secret，值就是环境变量 PB_ADMIN_SECRET 那份口令，不是某个频道的密钥
口令没配所有登录一律 403 forbidden，hint:"管理台未启用"。空 pb.admin.secret = 关掉整个管理台，这是没有 UI 开关的开关
口令错401 unauthorized，hint:"密钥错误"。比较是常量时间的（MessageDigest.isEqual），不回显你提交的内容
错到阈值429 login_locked + Retry-After 响应头，hint 是中文一句"失败次数过多，已临时锁定，请 N 秒后重试"。阈值与窗口复用摄入侧那两个键：pb.ingest.credential-fail-lock（默认 5）、pb.ingest.lock-window（默认 5m）
锁定计到哪只按来源 IP（X-Forwarded-For，由 Caddy 覆盖写入）计。计数是进程内 Caffeine 内存态：重启即清零，多实例各自算各自的。登录成功会清掉该 IP 的失败计数
token 形状HS256 JWT，sub:"admin"，有效期 24 小时。没有刷新接口——过期就重新登录。签名只验 HMAC 与 exp，库里不存 token
签名钥pb.admin.jwt-secret（PB_ADMIN_JWT_SECRET）。启动时硬校验：不能为空、至少 32 字节、必须与登录口令不同，否则容器直接起不来。生成：openssl rand -base64 32
携带方式此后每个请求 Authorization: Bearer <token>。缺这个头 → 401 hint:"缺少设备 token"；有头但验不过 → 401 hint:"管理 token 无效或已过期"

token 泄露了怎么办：没有吊销口

JWT 是无状态的，服务端不留任何 token 记录，因此没有"把这一张作废"的接口。唯一办法是换 PB_ADMIN_JWT_SECRET 并重启——这会同时作废所有已发出的 token（包括你自己手上那张）。这也是签名钥与口令必须分成两把的原因：共用一把时，连"轮换签名钥"都动不了。

另：管理 token 在鉴权层没有对应的设备行，鉴权通过后返回的 groupId 与 deviceId 都是字面量 "admin"。这一串在频道创建接口上有个实际后果，见 频道。

请求与响应的形状

  • 请求体字段是驼峰，响应字段是下划线。服务端把请求体反序列化成 Java record（channelNo、cronExpr、maxLevel、groupId），响应则是手写的 Map（channel_no、next_fire_at）。这不是风格分裂，是字面契约：往请求体里写 max_level 不会报错，会被静默忽略。
  • 未知字段一律忽略（fail-on-unknown-properties: false，全项目唯一一份 ObjectMapper 配置）。拼错键名没有任何提示——"我明明传了 cron 为什么报 cron_expr 必填"先核对驼峰。
  • 请求体上限：创建频道 8192 字节；定时任务 65536 字节（正文本身允许到频道的 max_body_bytes=32768，8KB 的通用上限会把合法任务挡在门外，所以这个口单独放宽）。超限 → 400 invalid_param，hint 是"请求体过大"。
  • 成功响应没有统一包装：每个端点自己决定键，但都带 "ok":true。
  • 错误响应恒为 {"ok":false,"error":"<code>","hint":"<string>"}。hint 永远不存在 null——没有提示时是空串 ""，写解析逻辑时别按可空处理。Retry-After 只在 429 出现。
  • GET /healthz 是这一组里唯一无鉴权的端点，但它不属于管理台：见入站 API。它会真的对数据库做一次 isValid（2 秒超时），本地存储模式还会往目录里写一个探测文件，任一项不通就回 503——所以它是就绪探针，不是存活探针。
HTTPerror本页里什么时候出现
400invalid_param请求体过大；GET /messages 的 q 为空或超 100 字符；定时任务的 content 空/超字节、cron_expr 缺失或非法、images 超 4 条或非 http(s)、目标频道已归档、channel_no 空
401unauthorized缺 Authorization 头；token 签名不对 / exp 已过。注意这与口令错同一个 code，靠 hint 区分
403forbidden只有一条：hint:"管理台未启用"（pb.admin.secret 为空）
404not_found频道、设备、任务不存在。hint 是资源名（"channel"、"scheduled task"），也可能是 ""——GET /channels/{channelNo} 与 DELETE /channels/{channelNo} 走的是不带 hint 的那一支
429login_locked登录口令错到阈值；带 Retry-After
500—未捕获异常；响应不带 stacktrace 与 message

频道

列表与详情

curl -s "$BASE/api/v1/admin/channels" -H "Authorization: Bearer $TOKEN" | jq '.channels[] | {channel_no, name, group_id, archived_at}'
curl -s "$BASE/api/v1/admin/channels/12345678" -H "Authorization: Bearer $TOKEN" | jq

GET /channels 每一项 = 详情里 channel 对象的那些键，再加 group_id。永远不含 secret——密钥只在建频道和重置那一次的响应里出现过，忘了就重置。

字段类型含义
channel_nostring8 位数字，服务端随机分配（长度 = pb.channels.channel-no-length）
namestring频道名；未命名时是 ""
group_idstring归属 Space。管理台是跨 Space 视图，这个字段是唯一能分清"这是谁的频道"的东西
max_levelstringinfo/warning/error：入站 level 会被向下截断到这个值
max_imagesnumber每条消息图片槽位上限，缺省 4
rate_limitnumber该频道每分钟条数，缺省 60（另有全局突发量 20）
max_body_bytesnumber正文上限，缺省 32768（UTF-8 字节，不是字符）
strict_auth0/1是否强制 ts/nonce/sign 三件套
muted0/1静音：照常入库下发，端上不出通知
daily_msg_limit / daily_image_limit / daily_bytes_limitnumber日配额，0 = 不限
sender_whitelist_mode0/11 = 只允许白名单里的 sender_id 写入
created_atnumberepoch 毫秒
archived_atnumber 或 null归档时间；null = 正常。列表只回未归档的，所以详情里的 archived_at 几乎总是 null——它是"这条还活着"的证明，不是提示

GET /channels/{channelNo} 回 {ok, channel, devices}：channel 是上面那张表加 group_id，devices 是已接入这条频道的设备（device_id、name、platform、group_id、created_at、last_seen_at——注意这一支不带 revoked_at，因为查询本身只挑未吊销的）。

建频道：POST /api/v1/admin/channels

curl -s -X POST "$BASE/api/v1/admin/channels" \
  -H "Authorization: Bearer $TOKEN" -H 'Content-Type: application/json' \
  --data-binary '{"groupId":"01J8ZK3Q7M2XW4V9HTNBSFY6PA","name":"Grafana 告警","maxLevel":"warning","maxImages":4}' | jq
字段（驼峰）必填实际行为
groupId强烈建议给频道落进哪个 Space。省略时落到字面量 "admin" 这个 Space（管理 JWT 没有设备行，鉴权层给的就是这个串）。后果：建出来的频道任何真实设备都看不到，入站能发、消息能存，客户端列表里永远没有它。这一层不校验 groupId 是否真的存在——写错了不会报错，只会造出一个孤儿频道
name可选trim 后截断 64 字符
maxLevel可选归一化到 info/warning/error；省略或写错（warn 也算错）→ 回落配置默认 pb.channels.default-max-level（默认 error）。静默降级，不报错
maxImages可选夹在 [0, 16]；省略 → pb.channels.default-max-images（默认 4）。超出范围或非数字才会 400，字段名写 max_images 则直接被忽略成默认值

响应 {ok, channel_no, secret, name, max_level, max_images}。secret 是 32 位小写十六进制（pb.channels.secret-bytes=16 字节随机数），有且只有这一次——库里存的是它的 sha256。当场存进密码管理器，丢了只能 rotate-secret（换新的，旧的立刻失效）。

重置密钥与归档

  • POST /channels/{channelNo}/rotate-secret — 无请求体。响应形状与建频道一样（新 secret 又只出现这一次）。顺手清掉该频道的凭据错误锁定计数：第三方凭据刚改对却被锁在 5 分钟窗口外的情况，这条是解药。频道不存在或不属于那个 group → 404 hint:"channel"。
  • DELETE /channels/{channelNo} — 响应 {ok, channel_no, archived_at}。这是软归档，不是删除：入站即刻 403，历史消息与媒体对象全部保留（按 D3），列表不再返回，订阅关系不动。想真删数据得走库，见安装与部署的保留期那一节。归档后想把第三方接回来只能重开——已归档频道不能作定时推送目标。
  • 频道治理位的修改（静音、白名单、日配额、strict_auth）不在本页：那几个键 PUT 在客户端 API 的 /api/v1/channels/{channelNo} 上（客户端 API），管理 token 用不了那个口。自带控制台因此也只能看不能改治理位。

设备

curl -s "$BASE/api/v1/admin/devices" -H "Authorization: Bearer $TOKEN" | jq '.devices[] | {device_id, name, group_id, last_seen_at, revoked_at}'
curl -s -X DELETE "$BASE/api/v1/admin/devices/01J8ZK3Q7M2XW4V9HTNBSFY6PD" -H "Authorization: Bearer $TOKEN"
  • GET /devices 跨所有 Space，每项：device_id、name、platform、group_id、created_at、last_seen_at、revoked_at（未吊销为 null）。不含任何密钥、token 或公钥。
  • DELETE /devices/{deviceId}：吊销。token 即刻失效、该设备的在线连接当场被踢，同一 Space 的其余端立刻收到一条 config/device_revoked 帧。设备号不存在 → 404（hint 为空串）。吊销不可逆：那台机器要回来只能重新注册或输恢复码。
  • 每 Space 设备上限（pb.devices.max-per-group，默认 5）是在注册侧卡的，这里看不到也不会改。

消息搜索：GET /api/v1/admin/messages

只读，跨 Space。注意路径就是 /messages，没有 /search 那一段——历史上这份文档写错过，脚本照抄会 404。

curl -s -G "$BASE/api/v1/admin/messages" \
  -H "Authorization: Bearer $TOKEN" \
  --data-urlencode 'q=构建失败' \
  --data-urlencode 'channel_no=12345678' \
  --data-urlencode 'type=markdown' \
  --data-urlencode 'since=1760000000000' \
  --data-urlencode 'limit=200' | jq '.count, .messages[0]'
query 参数必填实际行为
q必填非空且≤100 个字符（按码点计，中文一个字算一个），否则 400。匹配 body/title/summary 三者之一。%、_、\ 会被转义：搜 100% 就是字面的 100%，不会"匹配一切"
channel_no可选精确频道号
type可选对应库里的 msg_type：text/markdown/link/file。参数名叫 type、响应字段叫 msg_type，不一致是历史原因，照这里写
since可选，默认 0epoch 毫秒下限（created_at >= since）。不是 seq，跟 WS 重连的 since_seq 无关
limit可选，默认 50夹在 [1, 200]；传 500 不报错，按 200 执行。这个 200 是本端点自己写的常量，不受 pb.search.max-limit 影响

响应 {ok, count, messages}，按 seq 倒序（新→旧）。每条 14 个键：

{
  "seq": 1042, "msg_id": "01J8ZK…", "channel_no": "12345678",
  "channel_name": "Grafana 告警", "group_id": "01J8ZK…",
  "sender_id": "ci", "sender_name": "构建机",
  "msg_type": "markdown", "title": "unit-test 失败", "summary": "…", "body": "…",
  "level": "error", "media_status": "ready", "created_at": 1760000000000
}

没有分页游标，而且它是 LIKE '%…%'

客户端 API 那条历史链路有 after_seq 游标；管理台这条没有，一次最多 200 条，想更多只能缩小时间窗或换关键词。另外它不走 ngram 全文索引（pb.search.fulltext 对它无效），是三个 LIKE 条件的大扫描。数据量到几十万行以后，这个接口会明显慢——它是给"运维查一条"用的，不是给报表用的；趋势请看 /overview。

概览：GET /api/v1/admin/overview

curl -s "$BASE/api/v1/admin/overview" -H "Authorization: Bearer $TOKEN" | jq
{
  "ok": true,
  "stats": {
    "total_channels": 7, "active_channels": 6,
    "total_devices": 4, "active_devices": 3,
    "live_messages": 51234, "messages_today": 187
  },
  "trend": [ { "day": "2026-10-07", "count": 233 }, { "day": "2026-10-08", "count": 401 } ]
}
  • *_channels 的 active = 未归档；*_devices 的 active = 未吊销；live_messages = 未被软删除的行。
  • messages_today 的"今天"是服务端 JVM 默认时区的零点起算，不是 UTC。
  • trend 覆盖最近 14 天（含窗口内不足 14 天的情况），day 由 MySQL 的 DATE(FROM_UNIXTIME(...)) 按数据库时区格式化，count 升序逐日。零消息的那几天根本不出现在数组里（SQL GROUP BY 不会补零）——画图要么自己补，要么接受断档。

定时推送（6 个端点）

运维在服务端建任务（选频道 + 写正文 + 给 cron），服务端按时把消息灌进去。投递复用与外部 POST /message 完全同一条入库+下发链路，客户端分不出这条是谁发的——这是刻意的，定时推送不该有第二套语义。发送者固定记作 sender_id="scheduled"。

curl -s -X POST "$BASE/api/v1/admin/scheduled-tasks" \
  -H "Authorization: Bearer $TOKEN" -H 'Content-Type: application/json' \
  --data-binary @- <<'JSON' | jq .task
{
  "channelNo": "12345678",
  "name": "每晚巡检提醒",
  "title": "该跑 nightly-check 了",
  "content": "### 巡检\n1. 磁盘\n2. 证书",
  "level": "info",
  "senderName": "值守机器人",
  "images": ["https://example.com/chart.png"],
  "cronExpr": "0 30 21 * * *",
  "enabled": 1
}
JSON

请求体字段（驼峰）

字段必填实际行为
channelNo必填目标频道。空 → 400 channel_no 必填；不存在 → 404 channel；已归档 → 400「频道已归档，不能作为定时推送目标」。任务的 group_id 是从频道反查的，不是调用方给的——这里没有建频道那种孤儿 Space 风险
content必填非空，且按 UTF-8 字节不得超过该频道的 max_body_bytes（默认 32768）。按字节卡是为了和投递时同一把尺子：否则一个"3 万个汉字"的任务会创建成功、然后每分钟失败一次。超限 400，hint 里带实际字节数
cronExpr必填6 段：秒 分 时 日 月 周（Spring 的格式，不认 5 段 unix cron）。"每天 21:30" 写 0 30 21 * * *，不是 30 21 * * *。空 → 400 cron_expr 必填；段数或取值非法 → 400，hint 带 Spring 的原始报错；"已经没有下一次"（如过去的日期）→ 400
level可选创建时就归一化到 info/warning/error 并存归一后的值。写 warn 不会报错，会安静变成 info——所以列表里看到 level:"info" 而你以为给的是 warn，先检查拼写。触发时还会再过一遍频道 max_level 的向下截断
name / title / senderName可选分别 trim 后截断 64 / 512 / 64 字符；空串按 null 存，响应里回 ""
images可选外链数组，最多 4 条、单条 ≤1024 字符、只允许 http/https（data: 不行）。抓取与转存走入站那套异步流程（含 SSRF 闸），见入站 API → 图片
enabled可选省略 = 1（启用）；除 1 以外一律当 0。next_fire_at 由 cron 从当下往后算，不接受调用方指定

响应字段（下划线）

字段出现在含义
task_id、group_id、channel_no、name、title、level、sender_name、cron_expr、enabled、created_at、updated_at列表与详情都有enabled 是 0/1，不是布尔
channel_name只有列表列表查询 LEFT JOIN 了频道表带出来的名字；GET /scheduled-tasks/{taskId} 详情里没有这个键（详情走单表查询）。前端别指望详情响应里有频道名
content_head只有列表正文前 80 个字符。列表故意不回全文
content、images[]只有详情编辑弹窗要完整载荷就取详情；详情里没有 content_head
next_fire_at、last_fire_at、created_at、updated_at都有epoch 毫秒；空值回 0 而不是 null（"从没跑过"= last_fire_at:0）
last_result、last_error、last_msg_id都有last_result 是 "ok"/"failed"，没跑过时是 null。last_error 截断 255 字符；last_msg_id 是这条定时消息的 ULID，可以拿它去 /messages 或客户端 API 里核对到底发出去了没

启停、编辑与执行口径

# 停用 / 启用：只有 enabled 为 1 才算启用
curl -s -X POST "$BASE/api/v1/admin/scheduled-tasks/<task_id>/enabled" \
  -H "Authorization: Bearer $TOKEN" -H 'Content-Type: application/json' \
  --data-binary '{"enabled":0}' | jq '.task.enabled'

curl -s -X PUT "$BASE/api/v1/admin/scheduled-tasks/<task_id>" \
  -H "Authorization: Bearer $TOKEN" --data-binary @task.json | jq .task.cron_expr
curl -s -X DELETE "$BASE/api/v1/admin/scheduled-tasks/<task_id>" -H "Authorization: Bearer $TOKEN"
  • PUT 是整体覆盖，不是补丁。载荷与调度字段全量替换（没提交的字段会被清空），但 last_* 执行结果原样保留。改了 cronExpr 就按新表达式从当下重算 next_fire_at。
  • 重新启用会重算下次触发时间：停用三天的任务再打开，不会立刻补跑一堆，而是排到下一个 cron 时隙。
  • 调度是扫表 + next_fire_at 抢占，不是内存 Trigger：周期 pb.scheduled.sweep-interval（默认 15s，首轮延迟 20s），每轮最多 batch-size（默认 50）条。状态全在库里，所以重启不丢、多实例天然安全。
  • 精度到分钟，不是到秒。亚分钟级 cron 会被推迟到下个扫描点，且同一分钟时隙内多次触发共用一个幂等键（msg_key = sched:<task_id>:<分钟>），被唯一索引吃掉——实际效果是每分钟最多一条。别指望 0/5 * * * * * 每 5 秒一条。
  • 宕机几小时后只补当前这一次，不逐分钟回补，之后回到正常节律。
  • 投递失败会写 last_result:"failed" + last_error，不会停任务——它下个时隙还会再失败一次。目标频道中途被归档时，服务端会直接判"频道已归档或不存在，任务已自动停用"并把它置为停用，免得每分钟刷一条日志。
  • 删任务是真删（DELETE），已发出去的消息不受影响。

一次完整的运维流程

#!/usr/bin/env bash
# 依赖 curl + jq；服务端与口令从环境读，绝不写进脚本
set -euo pipefail
BASE="${PB_BASE:?例 http://127.0.0.1:8081}"
PB_ADMIN_SECRET="${PB_ADMIN_SECRET:?}"

TOKEN=$(curl -sS -X POST "$BASE/api/v1/admin/login" \
  -H 'Content-Type: application/json' \
  --data-binary "$(jq -nc --arg s "$PB_ADMIN_SECRET" '{secret:$s}')" | jq -er .token)

# 1) 找到目标 Space：从设备列表挑一个 group_id
GROUP=$(curl -sS "$BASE/api/v1/admin/devices" -H "Authorization: Bearer $TOKEN" \
  | jq -er '.devices[] | select(.revoked_at==null) | .group_id' | head -1)

# 2) 在该 Space 建频道，密钥当场落到文件（不要 print 到终端历史）
curl -sS -X POST "$BASE/api/v1/admin/channels" -H "Authorization: Bearer $TOKEN" \
  -H 'Content-Type: application/json' \
  --data-binary "$(jq -nc --arg g "$GROUP" '{groupId:$g,name:"nightly",maxLevel:"error",maxImages:4}')" \
  | jq -r '[.channel_no,.secret] | @tsv' > channel.tsv

# 3) 第三方入站口自己发一条验证链路
read -r NO SECRET < channel.tsv
curl -sS -X POST "$BASE/message" -H 'Content-Type: application/json' \
  --data-binary "$(jq -nc --arg c "$NO" --arg s "$SECRET" \
    '{channel:$c,secret:$s,content:"链路自测",level:"error",sender_id:"ops"}')"

# 4) 搜到它、并挂一个每晚任务
curl -sS -G "$BASE/api/v1/admin/messages" -H "Authorization: Bearer $TOKEN" \
  --data-urlencode 'q=链路自测' | jq '.count, .messages[0].msg_id'

curl -sS -X POST "$BASE/api/v1/admin/scheduled-tasks" -H "Authorization: Bearer $TOKEN" \
  -H 'Content-Type: application/json' \
  --data-binary "$(jq -nc --arg c "$NO" \
    '{channelNo:$c,name:"每晚提醒",title:"该跑巡检了",content:"见 cron",level:"info",cronExpr:"0 30 21 * * *"}') \
  | jq -r '.task.task_id, (.task.next_fire_at|tostring)'

三处细节是有意为之：口令与 body 用 jq -n 现拼，避免把密钥写进脚本正文；groupId 从真实设备反查，避免 建频道 那节说的孤儿 Space；频道号与密钥直接落文件，不进 shell 历史。

边界与已知取舍

  • 权限是全局的，没有分级。一个 token 能看所有 Space 的消息、吊销任何设备。没有"只读 token"、没有"限某个 Space 的 token"，也没有审计日志。
  • 这一组接口默认就是公网可达的。自带 deploy/Caddyfile 里没有任何一条关于 /api/v1/admin 的规则（它只把 /actuator/* 挡成 403），服务端的 InternalAccessFilter 也只管 /healthz 与 /actuator/**，够不着这里。换句话说：整组运维面的全部防线就是那一条口令 + 24 小时的 token。要按来源网段收口，得自己在前置的 Nginx / 防火墙加规则——这是部署时要主动做的一件事，不是配好了等你继承的。
  • 登录锁定只在进程内存里：重启清零、多实例各算各的。它挡的是"从一台机器上挂着字典慢慢试"，挡不住分布式慢速爆破——真正的防线是口令强度。
  • POST /channels 的 groupId 不做存在性校验（见 频道 那节）。这是已知设计缺口，不是文档没写完：目前唯一防线是操作者自己传对。
  • 自带控制台不调 POST /channels 与 rotate-secret——建频道与换密钥的正常路径是在 Android 客户端里做的（走客户端 API，密钥只回给那一台设备）。这两个管理端点是给脚本和救急留的。
  • GET /healthz 之外，本页所有端点都没有独立限流。滥用防线只有"token 得先拿到"这一条。
  • 时间字段一律 epoch 毫秒（除 trend[].day 是 yyyy-MM-dd 字符串），since 也是毫秒。时区口径分散在服务端 JVM 与 MySQL 两处，见 概览。
写消息进来看不到效果？先按 入站 API 排凭据与限流，再用本页的 消息搜索 确认落库，最后用 客户端 API 的 after_seq 增量拉取确认端上能不能读到。三套鉴权互不相通，卡在哪一层就查哪一层的文档。
