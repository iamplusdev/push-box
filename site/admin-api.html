管理台 API

管理台 API

这一组接口是自带 Web 控制台（web-admin/，Vue SPA）的后端契约，也是运维脚本唯一该用的口子。它同时是全库读写权限：跨 Space、能建频道、能吊销设备、能定时灌消息。请把它当运维口对待，不要当业务口用。

本页的"实测"是什么意思

标了实测的结论，是 2026-10-20 在一个真的跑起来的服务端上打出来的：WSL Docker 里的 pushbox-test 栈（prod profile，MySQL 8.4 + RustFS + Caddy，deploy/docker-compose-wsl.yml），16 个端点逐个调用、把响应的键集合原样打印出来比对文档。被测镜像构建自 3c3d764 那棵树（镜像时间戳 2026-10-19 23:57，傍晚只是用同一份镜像重建容器，二进制没变）。写本页时它与当时的 HEAD 在 server/src/main/java、web-admin/src 上逐字零差异。当晚 HEAD 又往前走了一步，所以这句话现在要加一条限定：HEAD 相对那套镜像多出的是坏请求体收口——写本页时它只有 AdminController 四处（下面那张表的"HEAD（已修）"一列）与 4 条单测，夜里又抬成共用工具 RequestBodyJson 并覆盖到设备侧那七处调用，一共 9 条单测；除此之外两边代码仍无差异；application-prod.yml 那边另有 server.port、pb.storage.type 两处变量消费，是配置管道，不影响响应形状。也就是说这套在跑的栈仍然是 500 那一版的行为，验证修复时是把新 jar docker cp 进去临时替换、打完矩阵再 --force-recreate 还原的（管理台四个端点与设备侧的 register/join 都这么打过，各前后一轮）。

没实测、只从代码读出来的，正文里都单独标了"按代码推断"。整页仍然没覆盖的：多实例部署下的锁定与扫表抢占、真机设备侧读到这些消息的完整链路、吊销一台设备之后 revoked_at 到底长成什么样、图片抓取（SSRF 闸与转存）在管理台侧的表现。反过来，定时任务的执行口径这次是等它真跑过轮子才写的：建了 0 * * * * * 的任务、看着它按分钟触发、成功轮的 last_result/last_msg_id、把目标频道归档以后下一轮自动停用，都是等出来的实测值。

选哪个口

给第三方系统发通知 → 入站 API 的 POST /message（一条 curl，凭据只有频道号+密钥，看不到别人的数据）。
自己做客户端（Android / Windows / 自研）→ 客户端 API（设备 token + Ed25519 签名 + 密封盒，只能看自己 Space）。
只有"管这台服务端"——列所有频道、搜所有消息、建定时任务——才是本页。

鉴权：一条口令换一个 24 小时的 JWT

与客户端 API 完全不同的两套机制：管理台不需要 X-PB-Device/Ts/Nonce/Sig 四个签名头，响应也不加密（明文 JSON，没有 sealed box）。代价是它没有任何"只读单个 Space"的余地——token 一验过，权限就是全局的。

POST   {base}/api/v1/admin/login  →  {"ok":true,"token":"<JWT>","expires_in":86400}

项实际行为
请求体{"secret":"<PB_ADMIN_SECRET>"}。字段名是 secret，值就是环境变量 PB_ADMIN_SECRET 那份口令，不是某个频道的密钥
口令没配所有登录一律 403 forbidden，hint:"管理台未启用"。空 pb.admin.secret = 关掉整个管理台，这是没有 UI 开关的开关
口令错401 unauthorized，hint:"密钥错误"。比较是常量时间的（MessageDigest.isEqual），不回显你提交的内容
错到阈值429 login_locked + Retry-After 响应头，hint 是中文一句"失败次数过多，已临时锁定，请 N 秒后重试"。阈值与窗口复用摄入侧那两个键：pb.ingest.credential-fail-lock（默认 5）、pb.ingest.lock-window（默认 5m）。阈值卡的是"第几次请求"而不是"第几次失败"：实测连续错 5 次，第 5 次照样回 401（锁定是在这一次里登记的），第 6 次才 429、Retry-After: 300，且 hint 里的秒数每次递减（300→299→…）。摄入侧不是这个节奏：同一套阈值下 POST /message 的第 5 次就直接 403 channel_locked（实测），两边经验别互相照抄。
锁定期内输对口令照样 429。锁的判定在比对口令之前，所以被锁的这台机器上"口令其实是对的"也进不去——看到 429 就等 Retry-After，别反复重试
（实测：错 6 次后立刻用正确口令登录 → 429 login_locked）
锁定计到哪只按来源 IP（X-Forwarded-For，由 Caddy 覆盖写入）计。计数是进程内 Caffeine 内存态：重启即清零（实测：重启容器后同一 IP 立刻能登），多实例各自算各自的。锁期一过，那条记录连同计数一起过期回收，下一次错误又从 401 开始数——不会留下"永久黑名单"，也不会"一错就再锁"。登录成功会清掉该 IP 的失败计数
token 形状HS256 JWT，sub:"admin"，有效期 24 小时。没有刷新接口——过期就重新登录。签名只验 HMAC 与 exp，库里不存 token
签名钥pb.admin.jwt-secret（PB_ADMIN_JWT_SECRET）。启动时硬校验：不能为空、至少 32 字节、必须与登录口令不同，否则容器直接起不来。生成：openssl rand -base64 32
携带方式此后每个请求 Authorization: Bearer <token>。两句 hint 的分工实测过：头整个缺失、Bearer 后面是空的、或者只写 token 忘了 Bearer 前缀 → 401 hint:"缺少设备 token"（这句是设备侧与管理侧共用的措辞，别被"设备"两个字带跑去查客户端签名）；有 Bearer 但内容验不过（乱码、被改过一个字符、只剩 header.payload 两段）→ 401 hint:"管理 token 无效或已过期"。缺前缀那一句特别容易误判成"鉴权坏了"

token 泄露了怎么办：没有吊销口

JWT 是无状态的，服务端不留任何 token 记录，因此没有"把这一张作废"的接口。唯一办法是换 PB_ADMIN_JWT_SECRET 并重启——这会同时作废所有已发出的 token（包括你自己手上那张）。这也是签名钥与口令必须分成两把的原因：共用一把时，连"轮换签名钥"都动不了。

另：管理 token 在鉴权层没有对应的设备行，鉴权通过后返回的 groupId 与 deviceId 都是字面量 "admin"。这一串在频道创建接口上有个实际后果，见 频道。

请求与响应的形状

  • 请求体字段是驼峰，响应字段是下划线。服务端把请求体反序列化成 Java record（channelNo、cronExpr、maxLevel、groupId），响应则是手写的 Map（channel_no、next_fire_at）。这不是风格分裂，是字面契约：往请求体里写 max_level 不会报错，会被静默忽略。
  • 未知字段一律忽略（fail-on-unknown-properties: false，全项目唯一一份 ObjectMapper 配置）。拼错键名没有任何提示——"我明明传了 cron 为什么报 cron_expr 必填"先核对驼峰。
  • 但尾部残留 token 会被判失败（同一份配置，fail-on-trailing-tokens: true，2026-10-21 起）：一段完整 JSON 后面再多一个字符、或多拼一个对象，请求体直接 400 invalid_param「请求体必须是合法 JSON」，不是"取前半段照常执行"。尾部只有空白与换行仍然放过（那不是 token）。这条只管 byte[] 端点：绑 record 的 POST /admin/login 与入站 POST /message 用的是 Spring 自己那份 mapper（服务端没有 Jackson2ObjectMapperBuilderCustomizer，覆盖不到），带尾部垃圾照样当合法 JSON 收下——所以别把"这套 API 对格式很严"推广到全部端点。同一份配置也是 WS 入站帧与管理台 JWT payload 解析用的那把尺子，改它等于改协议。
  • 查询参数反过来，是下划线：GET /messages 认 channel_no，写成 channelNo 不报错也不生效（实测：加了 channelNo=12345678 的搜索照样返回全部 Space 的命中）。同一份契约里，body 驼峰、query 与响应下划线。
  • 请求体上限：创建频道 8192 字节；定时任务 65536 字节（正文本身允许到频道的 max_body_bytes=32768，8KB 的通用上限会把合法任务挡在门外，所以这个口单独放宽）。超限 → 400 invalid_param。实测三档：POST /channels 9044 字节 → "请求体过大"；POST /scheduled-tasks 70064 字节 → "请求体过大（上限 65536 字节）"；40064 字节的任务体过了 64KB 这道闸、被正文配额挡下 → "正文 40000 字节，超过该频道的 max_body_bytes 32768"。
  • 成功响应没有统一包装：每个端点自己决定键，但都带 "ok":true。
  • 值为 null 的键根本不会出现，不是回 null。这组响应是手写的 Map 经全项目那份 Include.NON_NULL 的 mapper 序列化的，所以服务端 put("x", null) 之后 x 会被整个删掉。后果：同一类对象的键数不固定，判断"有没有值"要用键在不在（'title' in m），不能写 === null。本页两处实测撞见过：消息列表少 title、定时任务没跑过时少 last_result/last_error/last_msg_id。
  • 错误响应恒为 {"ok":false,"error":"<code>","hint":"<string>"}。hint 永远不存在 null——没有提示时是空串 ""，写解析逻辑时别按可空处理。Retry-After 只在 429 出现。
  • 但有三种情况拿到的错误体不是这个信封——脚本按 .error 取值会得到 null 而不报错。第一条已经被修掉了，后两条还在：
    • 畸形请求体在这四个口上返什么，取决于服务端是哪个版本。POST /channels、POST /scheduled-tasks、PUT /scheduled-tasks/{taskId}、POST /scheduled-tasks/{taskId}/enabled 把请求体当 byte[] 收、再自己调 Json.readBytes 反序列化，反序列化失败时抛的是 IllegalArgumentException，而全局异常处理只认三支（ApiException、HttpMessageNotReadableException、MissingServletRequestParameterException），接不住，于是原样冒到 Servlet 层。下面这张表左边是本页实测时那套镜像（3c3d764）的真实行为，右边是修好之后的行为：AdminController 内部加了 readJson(byte[], Class)，把这四处解析统一收口成 400 信封（措辞与 HttpMessageNotReadableException 那一支同一句话），没有动全局异常处理、也没有改成直接绑定 record——绑定 byte[] 是为了先量 8KB/64KB 上限，换成 record 就没地方量了。

    • GET /messages 的 since/limit 传非数字 → 400 Bad Request，同样是 Spring 默认体不是信封。
    • 路径写错（少了 /api/v1/admin 前缀）→ 404 也是默认体，见 端点总表 下面那段。
  • GET /healthz 是这一组里唯一无鉴权的端点，但它不属于管理台：见入站 API。它会真的对数据库做一次 isValid（2 秒超时），本地存储模式还会往目录里写一个探测文件，任一项不通就回 503——所以它是就绪探针，不是存活探针。

路径写错的三种下场，实测各不相同，哪一种都不会给你一句"这个端点不存在"：

  • 前缀整个漏掉 → HTTP 200 + 一个 HTML 页面。漏成 /admin/channels 实测回 200，body 是自带控制台那份 <!doctype html>（SPA 的兜底路由把任何不认识的路径都交给 index.html）。这是最阴的一种：状态码是 200，脚本按 if resp.ok 走下去了，取字段全 undefined，看起来像"服务端返回空数据"。所以别只看状态码，要验 Content-Type 或验 body 里有没有 ok 键。
  • 前缀对但末段拼错 → 404，但不是信封。末段拼成一个不存在的名字（/api/v1/admin/ 后面跟任何没实现的词）实测回 {"timestamp":…,"status":404,"error":"Not Found","path":…}，Spring 默认体、没有 ok/hint。而末段是合法资源名却不存在（如 /api/v1/admin/scheduled-tasks/NOPE）走的是应用自己的 404 → 信封 {"ok":false,"error":"not_found","hint":"scheduled task"}。同为 404，两种体。
  • 方法用错 → 405 非信封。实测向 /api/v1/admin/scheduled-tasks/<taskId> 发 POST（这个路径只有 GET/PUT/DELETE，启停要打到 …/enabled 上）→ {"status":405,"error":"Method Not Allowed","path":…}。注意方法匹配发生在资源存在性之前，所以任务号随便写也一样是 405，不会先 404。
  • 漏成 /api/v1/channels（少 admin 段）→ 401 信封，hint:"缺少签名头 X-PB-Device/Ts/Nonce/Sig"——那是设备签名那一套鉴权在说话，看起来像鉴权坏了，其实是走错了门。

建频道：POST /api/v1/admin/channels

curl -s -X POST "$BASE/api/v1/admin/channels" \
  -H "Authorization: Bearer $TOKEN" -H 'Content-Type: application/json' \
  --data-binary '{"groupId":"01J8ZK3Q7M2XW4V9HTNBSFY6PA","name":"Grafana 告警","maxLevel":"warning","maxImages":4}' | jq
字段（驼峰）必填实际行为
groupId必填频道落进哪个 Space，必须是 groups 表里真已有的一行（也就是至少有一台设备用它的 Space 口令注册过）。2026-10-21 起两种缺失都返 400 invalid_param：省略或全空白 → hint 缺少 groupId：频道要建在设备所在的那个 Space 下，否则设备查不到；写了一个不存在的 id（包括字面量 "admin"）→ hint groupId 不存在：这个 Space 里还没有设备注册过。改之前这里是不校验的，省略就回退到管理 JWT 那个虚拟的 "admin"，于是"建得过、存得下、任何真实设备都看不见"。首尾空白会被 trim 掉再落库（实测 " grp_xxx " 存成 grp_xxx）。怎么拿到合法的 id：从真实设备反查，GET /devices 的每台设备都带 group_id
name可选trim 后截断 64 字符
maxLevel可选归一化到 info/warning/error；省略或写错（warn 也算错）→ 回落配置默认 pb.channels.default-max-level（默认 error）。静默降级，不报错
maxImages可选夹在 [0, 16]；省略 → pb.channels.default-max-images（默认 4）。超出范围或非数字才会 400，字段名写 max_images 则直接被忽略成默认值

响应 {ok, channel_no, secret, name, max_level, max_images}——实测就这 6 个键，不回显 group_id：频道落在哪个 Space 得再 GET /channels/{channel_no} 查详情才知道。这条在 2026-10-21 之前更要紧——那时省略 groupId 也返 200、响应看起来完全正常，只有详情里那个字段是字面量 "admin"；现在这一条走不到了（省略直接 400，见上表）。

secret 是 32 位小写十六进制（pb.channels.secret-bytes=16 字节随机数），有且只有这一次——库里存的是它的 sha256。当场存进密码管理器，丢了只能 rotate-secret（换新的，旧的立刻失效）。

重置密钥与归档

  • POST /channels/{channelNo}/rotate-secret — 无请求体。响应形状与建频道一样（实测同样是那 6 个键、同样不回显 group_id；新 secret 又只出现这一次）。顺手清掉该频道的凭据错误锁定计数：第三方凭据刚改对却被锁在 5 分钟窗口外的情况，这条是解药。实测跑通了解药本身：把一条频道的密钥连错 5 次（摄入侧第 5 次就 403 channel_locked，之后连正确密钥也被挡在外面）→ rotate-secret 一次 → 新密钥当场 200 投递成功，旧密钥立刻 401 invalid_credential。频道不存在 → 404 hint:"channel"。
  • DELETE /channels/{channelNo} — 响应 {ok, channel_no, archived_at}（实测 archived_at 是 epoch 毫秒）。这是软归档，不是删除：入站即刻被拒（实测 POST /message → 403 channel_locked、hint 为空串——与凭据错到阈值同一个 code，见入站 API 的错误表），历史消息与媒体对象全部保留（按 D3），列表不再返回，订阅关系不动。"归档"只影响 GET /channels 那一张列表——实测归档后 GET /channels/{channelNo} 详情照样 200 回整条记录（archived_at 变非 null），/messages 也照样搜得到它的历史消息。想真删数据得走库，见安装与部署的保留期那一节。归档后想把第三方接回来只能重开——已归档频道不能作定时推送目标。
  • 频道治理位的修改（静音、白名单、日配额、strict_auth）不在本页：那几个键 PUT 在客户端 API 的 /api/v1/channels/{channelNo} 上（客户端 API），管理 token 用不了那个口。自带控制台因此也只能看不能改治理位。

设备

curl -s "$BASE/api/v1/admin/devices" -H "Authorization: Bearer $TOKEN" | jq '.devices[] | {device_id, name, group_id, last_seen_at, revoked_at}'

消息搜索：GET /api/v1/admin/messages

只读，跨 Space。注意路径就是 /messages，没有 /search 那一段——历史上这份文档写错过，脚本照抄会 404。

curl -s -G "$BASE/api/v1/admin/messages" \
  -H "Authorization: Bearer $TOKEN" \
  --data-urlencode 'q=构建失败' \
  --data-urlencode 'channel_no=12345678' \
  --data-urlencode 'type=markdown' \
  --data-urlencode 'since=1760000000000' \
  --data-urlencode 'limit=200' | jq '.count, .messages[0]'
query 参数必填实际行为
q必填非空且≤100 个字符，否则 400（hint 分别是 "q 不能为空"、"q 最长 100 字符"）。长度按 Unicode 码点算，不是 UTF-16 单元、也不是字节——实测 101 个汉字 400 / 100 个汉字 200，而 60 个 emoji（=120 个 UTF-16 单元、240 字节）照样 200。前后空白会先 trim 再用，实测同一个关键词两侧各加三个空格，命中数不变（都是 2）；纯空白按"必填"处理。匹配 body/title/summary 三者之一。%、_、\ 会被转义：实测库里有 a_b_c 时 q=a_c 命中 0 条——不转义的话这条 LIKE 会把它当单字符通配符匹上；搜 100% 同理是字面的 100%
channel_no可选精确频道号
type可选对应库里的 msg_type：text/markdown/link/file。参数名叫 type、响应字段叫 msg_type，不一致是历史原因，照这里写
since可选，默认 0epoch 毫秒下限（created_at >= since）。不是 seq，跟 WS 重连的 since_seq 无关
limit可选，默认 50夹在 [1, 200]；传 500 不报错，按 200 执行。这个 200 是本端点自己写的常量，不受 pb.search.max-limit 影响

响应 {ok, count, messages}，按 seq 倒序（新→旧）。下面是一个"满键"的形状，共 14 个键——但别按固定 14 个写解析：这一组响应走的是全项目那份 Include.NON_NULL 的 mapper，值为 null 的键整个不出现。实测同一批两条消息，一条 14 键、一条 13 键，少的正是没填的 title。代码侧这 14 个键里有四个来自可空列或 LEFT JOIN（title、summary、sender_name 取 senders.display_name、channel_name 取 channels.name），它们为 NULL 时同样会整个消失——实测只直接撞见过 title 缺席，其余四个是按列的可空性推出来的：

定时推送（6 个端点）

运维在服务端建任务（选频道 + 写正文 + 给 cron），服务端按时把消息灌进去。投递复用与外部 POST /message 完全同一条入库+下发链路，客户端分不出这条是谁发的——这是刻意的，定时推送不该有第二套语义。发送者固定记作 sender_id="scheduled"。

curl -s -X POST "$BASE/api/v1/admin/scheduled-tasks" \
  -H "Authorization: Bearer $TOKEN" -H 'Content-Type: application/json' \
  --data-binary @- <<'JSON' | jq .task
{
  "channelNo": "12345678",
  "name": "每晚巡检提醒",
  "category": "巡检",
  "title": "该跑 nightly-check 了",
  "content": "### 巡检\n1. 磁盘\n2. 证书",
  "level": "info",
  "senderName": "值守机器人",
  "images": ["https://example.com/chart.png"],
  "cronExpr": "0 30 21 * * *",
  "enabled": 1

JSON

请求体字段（驼峰）

字段必填实际行为
channelNo必填目标频道。空 → 400 channel_no 必填；不存在 → 404 channel；已归档 → 400「频道已归档，不能作为定时推送目标」。任务的 group_id 是从频道反查的，不是调用方给的——这里没有建频道那种孤儿 Space 风险
content必填非空，且按 UTF-8 字节不得超过该频道的 max_body_bytes（默认 32768）。按字节卡是为了和投递时同一把尺子：否则一个"3 万个汉字"的任务会创建成功、然后每分钟失败一次。超限 400，hint 里带实际字节数
cronExpr必填6 段：秒 分 时 日 月 周（Spring 的格式，不认 5 段 unix cron）。"每天 21:30" 写 0 30 21 * * *，不是 30 21 * * *。空 → 400 cron_expr 必填；段数或取值非法 → 400，hint 带 Spring 的原始报错；"已经没有下一次"（如过去的日期）→ 400
level可选创建时就归一化到 info/warning/error 并存归一后的值。写 warn 不会报错，会安静变成 info——所以列表里看到 level:"info" 而你以为给的是 warn，先检查拼写。触发时还会再过一遍频道 max_level 的向下截断
category可选管理台列表用的自由标签（公告 / 巡检 / 营销……），不是字典表：服务端只做 trim + 截到 32 字符，不校验取值、不报 400，空串与不填都是有效值且存成 ""（列是 NOT NULL DEFAULT ''，所以库里永远不会出现 null）。Flyway V9 加的列。别把它当枚举用——拼错的标签会安静地多出一个分类，管理台的筛选下拉是"从当前列表里现取选项 + 可以顺手新建"，没有独立的管理页
name / title / senderName可选分别 trim 后截断 64 / 512 / 64 字符；空串按 null 存，响应里回 ""
images可选外链数组，最多 4 条、单条 ≤1024 字符、只允许 http/https（data: 不行）。抓取与转存走入站那套异步流程（含 SSRF 闸），见入站 API → 图片
enabled可选省略 = 1（启用）；除 1 以外一律当 0。next_fire_at 由 cron 从当下往后算，不接受调用方指定

响应字段（下划线）

字段出现在含义
task_id、group_id、channel_no、name、category、title、level、sender_name、cron_expr、enabled、created_at、updated_at三种响应都有（列表、详情、写操作）enabled 是 0/1，不是布尔（实测 typeof 为 number）。name/title/sender_name 没填时回 ""，不是省略；category 没填同样回 ""，但它永远是字符串、不会出现 null 或键消失
channel_name只有列表列表查询 LEFT JOIN 了频道表带出来的名字；GET /scheduled-tasks/{taskId} 详情、以及 POST/PUT/enabled 三个写操作的响应里都没有这个键。键数现查，别信文档里抄的数字（这类数一改就烂）：jq '.tasks[0] | keys | length' 打列表、jq '.task | keys | length' 打详情与写响应。刚建、从没触发过的任务是 列表 16 / 详情 16 / 写响应 15（2026-10-21 加了 category 之后各 +1；少的那 3 个键是 last_*，见下面那条）。前端别指望详情响应里有频道名
content_head列表与写操作正文前 80 个字符。这两种形状故意不回全文
content、images[]只有详情编辑弹窗要完整载荷就取详情；详情里没有 content_head
next_fire_at、last_fire_at、created_at、updated_at都有epoch 毫秒；空值回 0 而不是 null，键也不会消失（实测从没跑过的任务 = last_fire_at: 0）
last_result、last_error、last_msg_id跑过之后才有，而且三个各自可能出现这三个不是"都有"：它们由服务端 put(null)，而那份 Include.NON_NULL 的 mapper 会把值为 null 的键整个删掉——实测一条刚建、还没触发过的任务，详情响应里三个键都不存在，不是回 null。所以"从没跑过"和"跑过但结果为空"在 JSON 里靠键在不在区分，前端 task.last_result === null 那种判断是写不出 true 的。跑过之后也不是三个一起出现：实测成功那一轮 = last_result:"ok" + last_msg_id（last_error 缺席），失败那一轮 = last_result:"failed" + last_error（last_msg_id 反而被清掉、键消失）。last_error 截断 255 字符；last_msg_id 是这条定时消息的 ULID，可以拿它去 /messages 或客户端 API 里核对到底发出去了没

启停、编辑与执行口径

# 停用 / 启用：只有 enabled 为 1 才算启用
curl -s -X POST "$BASE/api/v1/admin/scheduled-tasks/<task_id>/enabled" \
  -H "Authorization: Bearer $TOKEN" -H 'Content-Type: application/json' \
  --data-binary '{"enabled":0}' | jq '.task.enabled'

curl -s -X PUT "$BASE/api/v1/admin/scheduled-tasks/<task_id>" \
  -H "Authorization: Bearer $TOKEN" --data-binary @task.json | jq .task.cron_expr
curl -s -X DELETE "$BASE/api/v1/admin/scheduled-tasks/<task_id>" -H "Authorization: Bearer $TOKEN"
  • PUT 是整体覆盖，不是补丁。实测把一条填齐的任务只用 {channelNo, content, cronExpr} 覆盖一次：name、title、sender_name 全变 ""，images 变空数组，level 回落到 "info"（不是保留原值，也不是 error）。last_* 执行结果原样保留。改了 cronExpr 就按新表达式从当下重算 next_fire_at。所以编辑弹窗必须把详情读到的字段整个回填再 PUT，漏一个就静默清空一个。
  • 停用是真的停，重启会重算时隙——实测节奏：用 0 * * * * * 建一条、立刻停用，停着 70 秒期间 next_fire_at 就冻在那个已经过去了 55 秒的时隙上、一条也没发（last_result 缺席、last_fire_at 仍是 0）；再启用时 next_fire_at 从当下重算成下一个分钟时隙，没有把过去那个时隙补跑掉。停用三天的任务同理，排到下一个 cron 时隙，不会一开就刷一堆。
  • 调度是扫表 + next_fire_at 抢占，不是内存 Trigger：周期 pb.scheduled.sweep-interval（默认 15s，首轮延迟 20s），每轮最多 batch-size（默认 50）条。状态全在库里，所以重启不丢、多实例天然安全。
  • 精度到分钟，不是到秒。亚分钟级 cron 会被推迟到下个扫描点，且同一分钟时隙内多次触发共用一个幂等键（msg_key = sched:<task_id>:<分钟>），被唯一索引吃掉——实际效果是每分钟最多一条。别指望 0/5 * * * * * 每 5 秒一条。
  • 宕机几小时后只补当前这一次，不逐分钟回补，之后回到正常节律。
  • 投递失败会写 last_result:"failed" + last_error，不会停任务——它下个时隙还会再失败一次。唯一的例外是目标频道中途被归档：实测归档后下一轮扫表把任务 enabled 直接置成 0，last_result="failed"、last_error 原话 "频道已归档或不存在，任务已自动停用"，免得每分钟刷一条日志。
  • 还有一条实测到的细节：失败的那一轮会把上一轮成功留下的 last_msg_id 抹掉（该列写 null，于是键整个消失）。所以 last_msg_id 的语义是"最后一次尝试的消息 id"，不是"最后一条成功送达的消息"——想用它对账投递结果，得配合 last_result=="ok" 一起判。
  • 删任务是真删（DELETE），已发出去的消息不受影响。

一次完整的运维流程

#!/usr/bin/env bash
# 依赖 curl + jq；服务端与口令从环境读，绝不写进脚本
set -euo pipefail
BASE="${PB_BASE:?例 http://127.0.0.1:8081}"
PB_ADMIN_SECRET="${PB_ADMIN_SECRET:?}"

TOKEN=$(curl -sS -X POST "$BASE/api/v1/admin/login" \
  -H 'Content-Type: application/json' \
  --data-binary "$(jq -nc --arg s "$PB_ADMIN_SECRET" '{secret:$s}')" | jq -er .token)

# 1) 找到目标 Space：从设备列表挑一个 group_id
GROUP=$(curl -sS "$BASE/api/v1/admin/devices" -H "Authorization: Bearer $TOKEN" \
  | jq -er '.devices[] | select(.revoked_at==null) | .group_id' | head -1)

# 2) 在该 Space 建频道，密钥当场落到文件（不要 print 到终端历史）
curl -sS -X POST "$BASE/api/v1/admin/channels" -H "Authorization: Bearer $TOKEN" \
  -H 'Content-Type: application/json' \
  --data-binary "$(jq -nc --arg g "$GROUP" '{groupId:$g,name:"nightly",maxLevel:"error",maxImages:4}')" \
  | jq -r '[.channel_no,.secret] | @tsv' > channel.tsv

# 3) 第三方入站口自己发一条验证链路
read -r NO SECRET < channel.tsv
curl -sS -X POST "$BASE/message" -H 'Content-Type: application/json' \

三处细节是有意为之：口令与 body 用 jq -n 现拼，避免把密钥写进脚本正文；groupId 从真实设备反查，避免 建频道 那节说的孤儿 Space；频道号与密钥直接落文件，不进 shell 历史。

边界与已知取舍

  • 权限是全局的，没有分级。一个 token 能看所有 Space 的消息、吊销任何设备。没有"只读 token"、没有"限某个 Space 的 token"，也没有审计日志。
  • 这一组接口默认就是公网可达的。自带 deploy/Caddyfile 里没有任何一条关于 /api/v1/admin 的规则（它只把 /actuator/* 挡成 403），服务端的 InternalAccessFilter 也只管 /healthz 与 /actuator/**，够不着这里。换句话说：整组运维面的全部防线就是那一条口令 + 24 小时的 token。要按来源网段收口，得自己在前置的 Nginx / 防火墙加规则——这是部署时要主动做的一件事，不是配好了等你继承的。
  • 登录锁定只在进程内存里：重启清零、多实例各算各的。它挡的是"从一台机器上挂着字典慢慢试"，挡不住分布式慢速爆破——真正的防线是口令强度。实测它的节流粒度是"每个 5 分钟窗口 5 次机会"：窗口一到，那条计数记录连同锁期一起过期回收，攻击者又拿到一整轮 5 次（17:53 锁上、17:58 到期、17:59 再错三次全是 401，就是这个节奏）。换算下来单一来源 IP 约 60 次/小时、一夜约 1400 次，这道闸给字典攻击拖的时间并不长——所以本页那条"整组运维面的防线就是口令 + token"要说得更白：锁定的意义是限速，不是拦住。
  • 四个写端点的畸形请求体：实测时是 500，当晚已改成 400，夜里又把收口抬成了共用工具（详见"请求与响应的形状"那张表）。成因是 Json.readBytes 抛的 IllegalArgumentException 不在 GlobalExceptionHandler 的三支覆盖里，一路冒到 Servlet 层。当时的影响有两层：客户端拿到的不是统一信封（按 .error 取值得到 undefined），以及服务端错误日志与告警会被别人的手滑污染——运维看到 500 得先怀疑是不是请求体打错了。修法没走"改绑 record"也没走"全局补一支 IllegalArgumentException handler"：改绑 record 会把量 8KB/64KB 上限的地方一起删掉，后者会把不属于这一族的解析失败（比如 JWT payload）一并改掉。现在是 RequestBodyJson.read 与 readTree 两个方法，管理台四处、设备侧七处调用（八个端点）都过它；PUT /api/v1/channels/{channelNo} 走 readTree，因为它要区分"字段没提交"与"提交 null"。改之前查过客户端口径：Android 与 Windows 都不按状态码分档、非 2xx 时一个不解析错误体、一个宽容选读，也都没有幂等键，所以改它不会动到任何重试或身份逻辑，详见客户端 API的 500 那一行。有一处此前算错了：PUT /api/v1/state/read 自己就 catch 成 400，从来不是 500 源，所以"设备侧九处"是错的。
  • POST /channels 的 groupId 现在必填且要存在于 groups 表（见 频道 那节）。这条 2026-10-21 之前是不校验的，省略就落进设备永远查不到的 "admin" Space；当时已经建在 admin Space 里的频道不会被这次改动搬走，它们仍然只在管理台看得见，要让用户收到得在真实 Space 下重建一个再归档旧的。
  • 自带控制台不调 POST /channels 与 rotate-secret——建频道与换密钥的正常路径是在 Android 客户端里做的（走客户端 API，密钥只回给那一台设备）。这两个管理端点是给脚本和救急留的。
  • GET /healthz 之外，本页所有端点都没有独立限流。滥用防线只有"token 得先拿到"这一条。
  • 时间字段一律 epoch 毫秒（除 trend[].day 是 yyyy-MM-dd 字符串），since 也是毫秒。时区口径分散在服务端 JVM 与 MySQL 两处，见 概览。
