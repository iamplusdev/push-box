客户端 API（读取）

客户端 API：设备读取

这一套是给自己的设备用的：拉历史、搜全文、建频道、标已读、删除、取图片字节。与入站 API是两条完全不同的鉴权路径——第三方永远够不到这里。

两条鉴权路径

路径 A · 第三方写入

POST /message
凭据 = 频道号 + 频道密钥，只放 body
响应是明文 JSON
不涉加密材料

路径 B · 设备读写 本页

/api/v1/**
凭据 = 设备 token + Ed25519 请求签名
响应体一律过一次性密封盒
私钥不离开设备，服务端只存公钥

路径 B 的加密目标很明确：让服务端之外的人读不到消息正文——即使反代、日志、抓包都拿到 HTTPS 之外的东西也没用。它不是端到端加密：服务端为了能做中文全文检索，库里存的是明文。

请求鉴权四件套

位置内容校验
Authorization: Bearer <token>注册时下发的设备令牌令牌须存在、未吊销，且 device_id 与它匹配
X-PB-Device设备 ID与令牌指向的设备一致，否则 unauthorized
X-PB-Tsepoch 毫秒与服务端时间差 ≤ 300s，超出报 clock_skew
X-PB-Noncebase64，≥16 字节进 10 分钟去重缓存；重复报 409 replay
X-PB-Sigbase64 的 Ed25519 签名用设备注册时上传的 sign_pubkey 验；失败报 bad_signature

四个头缺任何一个都是同一句话（"缺少签名头"），缺哪个不告诉你。另外每个设备每分钟限 300 次且不叠突发。

签的是什么：canonical 字符串

逐字节拼出来的，换行分隔，UTF-8：

pushbox-rest-auth-v1
{deviceId}
{METHOD 大写}
{requestURI}
{原始 query 串，无 query 时是空行}
{sha256_hex(body)，无 body 时对空字节串取 sha256}
{ts}
{base64(clientNonce)}

四条最容易踩的：

  • path 是 getRequestURI()，含 servlet context path（默认空，配了 server.servlet.context-path 就要带上）。
  • query 是原始串，不是"解析后重新拼"。所以 GET /api/v1/search 的参数顺序固定为 q, channel_no, sender_id, type, since, limit——任何一端换序就整片验签失败。q 含中文/空格时必须先按百分号编码后的形态进 canonical，因为服务端看到的本来就是编码后的串。
  • 无 body 不等于不签：GET、DELETE、以及三个"点一下就行"的 POST（rotate-secret、reset-channel-no、rotate-recovery-code）都对空字节串的 sha256 取哈希。这一档在 Android 上还有第二个坑，见实现注意。
  • 长整型 1000 与字符串 "1000" 的 sha256 不同：ts 是数字，别用带引号的形态去拼。

响应：一次性密封盒

除两个字节接口外，所有 /api/v1 响应体都被包成同一个信封：

{
  "v": 1,
  "eph_pub": "base64(32B X25519 临时公钥)",
  "salt":    "base64(32B = sha256(eph_pub))",
  "data":    "base64(AES-256-GCM 密文)",
  "n": 0
}

客户端用自己的 enc 私钥与 eph_pub 做 X25519 → HKDF 派生出 K → 以 n 为 nonce、AAD=n 解开。每次响应现场生成一对临时密钥，所以一次请求一个会话，没有跨请求的帧计数器。

两个例外：字节接口不是密封盒

GET /api/v1/media/{msgId}/{idx} 与 GET /api/v1/avatars/{token} 返回的是原始字节 + 真实 Content-Type + Cache-Control: no-store。图片要直接喂给系统图片解码器，套一层 base64 信封只会白白多一倍流量。它们仍然完整鉴权（Bearer + 四签名头），只是响应不加密——传输保护交给 TLS。

端点全表

下表"鉴权"列：开放 = 只按来源 IP 限流；设备 = 上面那套签名。注意连 register/join 的响应也是密封盒——因为 token 与恢复码等价于账号口令。

频道（App 是唯一控制台，没有 Web 管理台）

方法 · 路径鉴权说明
POST /api/v1/channels设备body：name?、max_level?、max_images?。响应带 secret，仅此一次
GET /api/v1/channels设备频道面（channels[] + 根上的 subscribed_only），永远不含 secret。每一项恒带 subscribed（这台设备接没接入这条），一条都没接入时是全 false 而不是缺这个键
POST /api/v1/channels/join设备body：{channel_no, secret} → 同一 Space 内接入这条频道。回该频道的治理面 + subscribed_only，不含 secret。错密钥 401；未知号码 / 别组 / 已归档一律 404（不给枚举频道号留缝）；空号码 400。重复接入幂等
POST /api/v1/channels/leave设备body：{channel_no}。取消接入，幂等：没接入过也回 200，removed:false
POST /api/v1/channels/subscription-mode设备body：{subscribed_only: 0|1}。切换这台设备的投递过滤器，回服务端实际生效值（客户端以此为准，别用自己刚发出去的那个）。填 2、-1 之类一律 400
PUT /api/v1/channels/{no}设备治理位 patch，11 个字段见下表。未提交的字段保持原值
POST /api/v1/channels/{no}/rotate-secret设备无请求体。回新 secret；旧 secret 即刻作废
POST /api/v1/channels/{no}/reset-channel-no设备无请求体。换发新对外号码，旧号即刻作废，历史随迁、密钥不变；回新号 + old_channel_no
DELETE /api/v1/channels/{no}设备归档：停止接收新消息（第三方收 403），历史保留，不可撤销
GET /api/v1/channels/{no}/capacity设备该频道消息数、正文字节数、图片数、图片字节数、最早一条时间
GET /api/v1/channels/{no}/senders设备白名单条目（含已停用的）
POST /api/v1/channels/{no}/senders设备body：{sender_id, enabled?}。enabled 省略＝加上并能发；显式 false 是停用而不是删除

PUT /channels/{no} 可提交：name、max_level、max_images、rate_limit、max_body_bytes、strict_auth、muted、daily_msg_limit、daily_image_limit、daily_bytes_limit、sender_whitelist_mode。数字型治理位填 0 表示沿用服务端默认值，而 muted/strict_auth/sender_whitelist_mode 是 0/1 位，0 就是"关"，不是"没配"。

接入是投递过滤器，不是权限边界

写一条频道凭 channel_no + secret，读一条频道凭设备 token——join 用的是前者，所以它只证明"我有权往这条频道发"，然后服务端把这条频道记进这台设备的订阅集。跨 Space 的频道即使知道密钥也接不进来（404），因为那会把"凭一串数字读到别人历史"变成第二条读路径。

subscribed_only=0（默认）＝这台设备收本 Space 全部频道；=1 时实时帧、WS 回放、REST 历史与搜索一起只走已接入的频道。因此开了过滤又一条没接入就是收不到任何内容——界面上要把这句话讲出来，别让人对着一个安静的图标找 bug。

两条刻意的口径：建频道的那台设备默认接入自己刚建的那条（否则"新建 → 开过滤"会把自己静默掐断）；接入之后连接入前的消息也拉得到（过滤按频道，不按接入时刻）。

消息、已读与删除

方法 · 路径参数 / body说明
GET /api/v1/messagesafter_seq=0 · channel_no? · limit=200（夹到 1..500）增量补拉；after_seq=0 即全量恢复历史。回 {messages[], tombstones[], latest_seq, has_more}

DELETE /api/v1/messages/{id}—标 tombstone + 图片标待删 + 广播 tombstone{id}。回 {ok, id, deleted_at}
DELETE /api/v1/messageschannel_no 必填 · sender_id?带 sender_id 清该会话；省略则清整个频道。回 {ok, channel_no, sender_id, deleted, deleted_at}
GET /api/v1/searchq 必填 · channel_no? · sender_id? · type? · since? · limit?服务端全文搜索（中文 ngram）。回 {results[], has_more}，每条只有 snippet 不含全文

清空是"一条 UPDATE + 一条 scope 帧"，不是逐条删除

一个会话可能上千条：逐条既打爆 SQL 往返，也会让其他端收到上千帧。所以 sender_id 为空的 scope 删除会下发 tombstone{scope:{channel_no, sender_id:null}}，客户端据此清掉该频道下所有会话。

幂等：会话本来就空或已清空时回 deleted=0，不报 404——客户端重试不该看到"不存在"。

客户端侧错误码

HTTPerrorhint怎么处理
401unauthorized缺头 / 设备无效或已吊销 / bad_signature / clock_skew / nonce 长度不足 / ts 必须是 epoch 毫秒只有"设备无效或已吊销"该清本地身份，其余（尤其 clock_skew）清了等于自杀，只能校时或修签名
409replay—nonce 撞了，换新 nonce 重签一次即可
409device_limit_reached—Space 已满 5 台，先吊销一台
404not_found是槽位状态机的一部分，不是随便写的调试文本：媒体接口回 pending/ready/failed/deleted/purged；头像接口只回 avatar按 hint 而不是状态码分支：purged 就别重试，pending 值得稍后再取
429rate_limited可重试秒数每设备 300/min，正常客户端撞不到；撞到了说明有循环
400invalid_param具体到字段唯一会明确告诉你哪里不对的一类

跨组访问与"记录不存在"回同一句话（媒体接口就是这么做 group_id 校验的）：不给探测别人组的消息 ID / 头像 token 是否存在留缝隙。

实现注意（写新客户端时先看这四条）

  1. 空 body 的 POST 不能只换 method。OkHttp 会拒"有 body 却没设 BodyPublisher"，也会拒"POST 复用 GET 请求"。rotate-secret、reset-channel-no、rotate-recovery-code 三处必须显式带空体。（对照：.NET 本来就允许无体 POST，所以 Windows 端没有这个分支。）
  2. canonical 里的 query 必须是原始串。别用"解析成 map 再拼"的结果——服务端拿的是 getQueryString()，顺序与编码都保持客户端发出的形态。
  3. 先验签再落库，失败不留半条。注册响应里 server_pub_fp 是 TOFU 固定用的：首连记下，之后指纹变了就该拒绝而不是"确认一下"。
  4. 已读游标只增不减。服务端对 read_state 是后写覆盖并广播 read 帧，一个迟到的旧帧就能把游标退回去；单调性得由客户端守。

怎么确认自己实现对了

签名与加密这类东西，"看起来实现了"和"逐字节一致"之间隔着一整片联调地狱。三处对齐手段按优先级用：

手段位置覆盖
测试向量testvectors/vectors.jsoninputs / signatures / rest_auth / sealed_box / frame / ratchet / summary。跨语言唯一真正可靠的对齐手段，固定输入固定期望输出
协议单测Windows dotnet test 的 ProtocolVectorsTest把上面每个 key 断一遍。新客户端可以照抄这个测试当验收
参考实现core/（Java，三端共用）与 windows/PushBox.Windows/Crypto（C#）SignatureTargets、FrameChannel、X25519、Ed25519、B64、Summary。Android 通过 :pbcore 直挂 ../core/src/main/java，与同源，不存在两份实现漂移
端到端探针deploy/probe/p0-e2e.mjs23 条判据跑在真服务端上（注册、签名、密封盒、重放、宽限期真删、逐设备接入过滤…）。新客户端拿它当"服务端到底要什么"的可执行答案

手工调一条读接口基本不可能——签名要现算、响应要私钥解。要试，就 clone core/ 当库用。

典型流程（带字段名，便于对照）

# 1. 首启注册（响应是密封盒，解开后才有这些键）
POST /api/v1/devices/register
  {enc_pubkey, sign_pubkey, name, platform}
  -> {device_id, group_id, token, recovery_code, server_pub_fp}

# 2. 建频道
POST /api/v1/channels  {name:"服务器告警", max_level:"error"}
  -> {channel_no, secret, ...}        # secret 只出现这一次

# 3. 第三方写入（换到路径 A，不再需要设备签名）
POST /message  {channel, secret, content, level:"error", sender_id:"grafana"}

# 4. 增量补拉（after_seq 用自己存的水位）
GET /api/v1/messages?after_seq=1041&limit=200
  -> {messages[], tombstones[], latest_seq, has_more}

# 5. 打开会话即置已读
PUT /api/v1/state/read  [{"channel_no":"12345678","sender_id":"grafana","last_read_seq":1042}]

# 6. 图片与头像（原始字节，仍带签名头）
GET /api/v1/media/{id}/0?size=thumb
GET /api/v1/avatars/{sha256_hex(sender_id)}

# 7. 全文搜索（服务端 ngram；参数顺序不能动）
GET /api/v1/search?q=CPU&channel_no=12345678&since=0&limit=50
