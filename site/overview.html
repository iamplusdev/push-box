概览

把告警、CI、脚本的消息，推送到你自己的设备上

一条 POST /message 投进服务端，PushBox 负责存下来、抓图转存、加密下发——你的 Android 手机与 Windows PC 几乎同时收到通知。不接厂商推送、不经第三方转发，消息与图片全在你自己的机器上。

49 ms受理 → 通知到账（同机 MySQL 实测，验收线 1s）
3 端Java 服务端 · Android Compose · Windows WPF
0需要额外账号的服务依赖（只有 MySQL 8 与一个 S3 兼容桶）

它是怎么串起来的

你的程序Grafana、CI、cron、内网服务，只需一个频道号 + 密钥
受理校验凭据、幂等、分配 seq、生成摘要，立即 200 回执
抓图转存外链图片并发抓取 → 缩略图 → 存进对象存储（不等它，超预算先出正文）
加密下发每台设备自己的会话钥加密同一帧，多端同时到达
客户端入库、出通知、点进会话把已读报回去，别的端红点随之消失

单向接收：气泡统一左对齐，不做"发送方/接收方"双色。level 只用气泡左侧 3px 色条与会话行小圆点表达； 四张图排 2×2（不是横排长条），每一格的状态独立——抓取失败的格子可以单独重试，其余照常渲染。

信任边界：为什么服务端是明文

  • 服务端 → 客户端这一跳是加密的。每台设备一对 X25519 + Ed25519，WS 帧走 HKDF 派生的 AES-256-GCM 通道，REST 响应走一次性 sealed-box。链路中间人拿不到正文。
  • 服务端库里是明文，这是刻意的。只有这样 MySQL 全文索引才能命中正文、服务端才能生成摘要、才能替你把外链图片抓下来转存。
  • 端到端加密已被否决：它的代价正是上面这三件核心功能。
  • 频道密钥只能写不能读。拿到 secret 的人能替你往这个频道推，但读不到任何历史；读历史需要设备密钥或恢复码。
  • 生产环境请上 HTTPS（deploy/Caddyfile 给了自签与 Let's Encrypt 两条路）。TLS 补的是"服务端本身可信"这一环，与帧加密互不替代。

功能

图文同帧

外链图片服务端抓取、生成缩略图、转存对象存储，并在合并窗口（默认 3s）内把图文并进同一条消息帧下发。

多端同时收到 + 已读同步

一个 Space 里几条频道、几台设备，同一条消息给每条在线连接各封一份信封（各自的会话钥与帧序号），手机与 PC 几乎同一秒到账。手机点进会话，PC 的红点在几十毫秒内消失；反向亦然。游标只增不减，服务端 last-write-wins 不会把它点亮回去。

全文搜索

MySQL ngram 全文 + 客户端本地索引两段合并，输入即查、回车补齐全部历史，命中可定位到那一条消息。

频道治理

按频道限级别、限图片数、限正文长度、限频率与每日配额、白名单发送者、严格签名鉴权、归档与清空。每台设备还能只挑自己要收的频道：凭频道号 + 密钥接入，再打开「只接收已接入的频道」（默认关，逐设备生效）。

断线不丢

重连带 since_seq，服务端按批循环补拉到取空才回 resume_ok；落后过多转 REST 回放。离线那台不靠轮询兜底：PC 只有退避重连（1s→60s）这一条路，Android 的 WorkManager 15 分钟一轮只在省电/轮询模式下生效。

换机找回

一个恢复码 = 加入同一个 Space 并回放全部历史（1 万条实测 <30s）。恢复码可随时轮换，旧码立即失效。

三分钟跑起来

cp deploy/env/prod.env.example deploy/env/local.env     # 填 PB_DB_PASSWORD / PB_S3_*
JAVA_HOME=/path/to/jdk-21 mvn -B -DskipTests package    # 产出 server/target/pushbox-server-1.1.0.jar
bash deploy/run-dev.sh                                  # 默认 8080，脚本自己 source local.env
node deploy/probe/p0-e2e.mjs                            # 端到端验收：看末行 N/N，且 0 失败

然后发第一条消息（入站接口是 POST {base}/message，不在 /api/v1 下，凭据在 body 里）：

curl -sS http://127.0.0.1:8080/message \
  -H 'Content-Type: application/json' \
  --data-binary @payload.json

字段全表、响应形状、错误码与一个可改参数实时生成 curl 的工具，都在 入站 API。三端各自的安装步骤见 安装与部署。

常见问题

能不能用它当个人微信 / 聊天工具？

不能。它是单向接收的：只有第三方 POST /message 写入，客户端没有发送框。会话按"频道 + 发送者"分组，只是为了把不同来源的告警摊开。

同一个频道，手机和电脑能同时收到同一条推送吗？

能，只要它们是同一个 Space 里的两台设备。消息只落库一次（一个全局 seq），服务端随后给这个 Space 里每一条在线连接各封一份信封——各自的会话钥、各自的帧序号，所以两端拿到的是同一条明文、两条互不相干的密文，几乎同一秒到账。两个坑：身份文件不能拷（会话表按 device_id 唯一，同一个 device_id 的新连接会顶掉旧的，症状是"只有一端收得到"且全程不报错）；两端唯一会长期不一致的地方是某一端开了「只接收已接入的频道」。细节见 使用说明 → 一个频道，两台设备同时收到。

同一个 Space 里别人建的频道，能让这台设备只看其中几条吗？

能。每台设备有一张自己的接收集：在频道页用频道号 + 密钥「加入频道」，再打开「只接收已接入的频道」（默认关，也就是全收）。开了之后没接入的频道照投、照入库，只是不再下发到这台设备——实时帧、断线补发、历史与搜索四处一起过滤。它是投递过滤器不是权限边界：跨 Space 的频道号即使密钥正确也一律 404。细节在 使用说明 与 客户端 API。

服务端挂了会丢消息吗？

投递侧会——第三方那次 POST 拿不到 200 就是没受理（重试请用同一个 msg_key，服务端按它幂等）。已经受理过的消息永久保留在库里，设备重连后按游标补齐。

为什么我的中文消息正文被截断了？

单帧超过 pb.ws.frame-max-bytes（默认 32KB）时服务端会二分定位安全长度削正文并置 truncated:true，客户端随即用 GET /api/v1/messages/{id} 回捞全文。按"超出多少字节就删多少个字符"的老写法，纯中文会一次删掉三倍需求量。

能在公网上裸跑 HTTP 吗？

不建议。帧加密保证了链路上读不到正文，但入站凭据 secret 是在 body 里明文送的，且浏览器/系统对 HTTP 的降级与中间设备行为不可控。请上 HTTPS，或把入站口只开在内网。
