管理台 API

管理台 API

服务端自带 Web 控制台走的就是这一组接口。它用来管这台服务端：列所有频道、吊销设备、跨 Space 搜消息、建定时推送。

Bearer JWT只用一个 Authorization 头，不需要设备签名头
24 小时token 有效期；没有刷新接口，过期就重新登录
全局读写一个 token 能看所有 Space，也能改所有 Space

先确认要用哪个口

  • 给第三方系统发通知 → 入站 API 的 POST /message，凭据只有频道号 + 密钥。
  • 自己写 Android / Windows 客户端 → 客户端 API，只能看自己那个 Space。
  • 管这台服务端 → 本页。

登录拿 token

  1. 在安装页里填一个管理台口令 
    安装页 →「管理台口令」→ 至少 8 个字符（推荐 openssl rand -base64 32）
    口令落在配置文件的 admin.password。留空是一个合法状态：管理台整个关闭，下面这些接口一律回 403「管理台未启用」，客户端收发不受影响。签 token 的那把密钥（admin.jwtKey）不用你填——服务端自动生成并回写配置文件，所以没有"两把钥必须不同且各 32 字节"这种要记的东西。管理台只认这一份口令，不是某个频道的密钥。
  2. 用口令换 token 
    BASE=http://127.0.0.1:7404          # 换成你的服务端地址
ADMIN_PASSWORD='<安装页里填的那个口令>'   # 只是本脚本的局部变量，服务端不读环境变量

TOKEN=$(curl -sS -X POST "$BASE/api/v1/admin/login" \
  -H 'Content-Type: application/json' \
  --data-binary "$(jq -nc --arg s "$ADMIN_PASSWORD" '{secret:$s}')" \
  | jq -er .token)
    请求体字段名是 secret。成功是 200，响应形如 {"ok":true,"token":"<JWT>","expires_in":86400}。口令经 jq 现拼，不落进脚本正文。
  3. 之后每个请求都带上 Bearer 头 
    curl -sS "$BASE/api/v1/admin/channels" \
  -H "Authorization: Bearer $TOKEN" | jq '.channels | length'
    成功是 200 且有 "ok":true。这一条通了，其余端点的鉴权就都通了。

登录这一发会出现的结果

HTTPerrorhint该怎么办
200——取 token，24 小时内不用重复登录
401unauthorized密钥错误口令不对；确认传的是安装页里填的那个管理台口令，而不是某个频道的密钥
401unauthorized缺少设备 tokenAuthorization 头没带上，或缺了 Bearer 前缀
401unauthorized管理 token 无效或已过期token 过期或被改动，重跑第 2 步
403forbidden管理台未启用安装页里那个管理台口令留空了，整个管理台处于关闭状态
429login_locked失败次数过多，已临时锁定…按响应头 Retry-After 的秒数等，锁定期内输对口令也是 429
  • 锁定按来源 IP 计：默认错满 5 次登记锁定，锁 5 分钟，就是 pb.ingest.credential-fail-lock 与 pb.ingest.lock-window 两个配置项。触发锁定那一次仍回 401，下一次才看到 429。
  • 计数存在进程内存里：服务端重启即清零，多实例各自算各自的。
  • 登录成功会清掉该来源 IP 的失败计数。

token 泄露了只能换签名钥

服务端不存任何 token 记录，因此没有"作废某一张 token"的接口。唯一办法是换掉配置文件里的 admin.jwtKey 并重启，这会连你自己手上那张一起作废。

请求与响应的约定

  • 请求体字段是驼峰：channelNo、cronExpr、maxLevel、groupId。
  • 响应字段和查询参数是下划线：channel_no、next_fire_at、channel_no。
  • 请求体里写错键名不报错、直接忽略，然后按默认值走。报「cron_expr 必填」时先检查是不是写成了下划线。
  • 成功响应没有统一包装，但都带 "ok":true。
  • 值为 null 的键整个不出现，不是回 null。判断"有没有值"要写 'title' in m，不能写 === null。
  • 错误响应恒为 {"ok":false,"error":"<code>","hint":"<string>"}；hint 没有提示时是空串 ""，不会是 null。Retry-After 只在 429 出现。
  • 时间字段一律 epoch 毫秒（只有 /overview 的 trend[].day 是 yyyy-MM-dd 字符串）。
  • 请求体上限：建频道 8192 字节，定时任务 65536 字节，超限 400。

错误码

HTTPerror什么时候出现
400invalid_param必填字段缺失或非法、请求体过大、q 为空或超 100 字符
401unauthorized没带 Authorization 头、token 验不过或已过期、口令错
403forbidden管理台未启用（安装页里的管理台口令留空）
404not_found频道、设备、任务不存在；hint 是资源名，也可能是空串
429login_locked登录失败到阈值；带 Retry-After

超限、超配额这类拒绝，hint 里带数字，可以直接正则取出来：

请求体过大
请求体过大（上限 65536 字节）
正文 40000 字节，超过该频道的 max_body_bytes 32768

三种情况你拿到的不是上面那个错误体，脚本按 .error 取值会得到 undefined：

  • GET /messages 的 since / limit 传非数字 → 400，没有 ok / hint。
  • 路径末段拼错，或该用 PUT 的地方发了 POST → 404 / 405，同样不是错误体。
  • 漏掉 admin 那一段（写成 /api/v1/channels）→ 401 hint:"缺少签名头 X-PB-Device/Ts/Nonce/Sig"。那是设备接口在说话，你走错了门。

频道

建一个频道

  1. 先拿到一个真实存在的 Space id 
    curl -sS "$BASE/api/v1/admin/devices" -H "Authorization: Bearer $TOKEN" \
  | jq -r '.devices[] | .group_id' | sort -u
    频道必须建在已经有设备注册过的那个 Space 下，否则服务端回 400，设备也永远看不到这条频道。
  2. 建频道，密钥当场存下来 
    curl -sS -X POST "$BASE/api/v1/admin/channels" \
  -H "Authorization: Bearer $TOKEN" -H 'Content-Type: application/json' \
  --data-binary "$(jq -nc --arg g "$GROUP" \
    '{groupId:$g,name:"Grafana 告警",maxLevel:"warning",maxImages":4}')" | tee channel.json
    期望 200。secret 只在响应里出现这一次，库里存的是它的哈希。丢了只能重置。
  3. 确认归属和接入设备 
    curl -sS "$BASE/api/v1/admin/channels/$(jq -r .channel_no channel.json)" \
  -H "Authorization: Bearer $TOKEN" | jq '.channel.group_id, .devices'
    建频道与重置密钥的响应不回显 group_id，要看落在哪个 Space 就查一次详情。

建频道的请求体

字段（驼峰）必填说明
groupId必填目标 Space 的 id，必须是设备已注册过的那个
name可选频道名，去空白后最长 64 字符
maxLevel可选info / warning / error；省略或写错都回落默认值 error
maxImages可选取值 0~16，省略默认 4

响应固定这 6 个键，secret 是 32 位小写十六进制：

{
  "ok": true,
  "channel_no": "12345678",
  "secret": "9f3c1e7ba20d4c6fe8510a9c73db2f14",
  "name": "Grafana 告警",
  "max_level": "warning",
  "max_images": 4
}

频道字段

列表里每一项就是这张表，再加上 group_id；详情还会再带一份 devices[]。任何读路径都不含 secret。

字段类型含义
channel_nostring8 位数字频道号，服务端随机分配
namestring频道名；未命名时是 ""
group_idstring归属 Space；管理台是跨 Space 视图，靠它分辨频道是谁的
max_levelstring入站 level 会被向下截断到这个值
max_imagesnumber每条消息图片上限，默认 4
rate_limitnumber该频道每分钟条数，默认 60
max_body_bytesnumber正文上限，默认 32768 字节（UTF-8）
strict_auth0/1是否强制 ts / nonce / sign 三件套
muted0/1静音：照常入库下发，端上不出通知
daily_msg_limit / daily_image_limit / daily_bytes_limitnumber日配额，0 = 不限
sender_whitelist_mode0/11 = 只允许白名单里的 sender_id 写入
created_atnumber创建时间，epoch 毫秒
archived_atnumber，或这个键不出现归档时间；活频道里这个键整个不存在，判断"活着"写 !("archived_at" in c)

详情里的 devices[] 每项是 device_id、name、platform、group_id、created_at、last_seen_at，只列未吊销的设备。

重置密钥与归档

curl -sS -X POST "$BASE/api/v1/admin/channels/12345678/rotate-secret" \
  -H "Authorization: Bearer $TOKEN" | jq .secret

curl -sS -X DELETE "$BASE/api/v1/admin/channels/12345678" \
  -H "Authorization: Bearer $TOKEN" | jq .archived_at
  • 重置密钥：无请求体，响应形状与建频道一样，新密钥又只出现这一次，旧密钥立刻失效。
  • 重置顺带清掉该频道的凭据错误锁定计数：第三方刚改对密钥却被锁在窗口外，跑这一条就解开。
  • 频道不存在 → 404，hint:"channel"。
  • 归档是软归档：入站立刻被拒，历史消息和媒体都还在，GET /channels 不再返回它。
  • 归档后详情 GET /channels/{channelNo} 照样 200，archived_at 变成非空；搜索也照样命中它的历史。
  • 已归档的频道不能作定时推送目标，也不能在管理台恢复。
  • 治理位（静音、白名单、日配额、strict_auth）不在这一组接口上改：那几个键在 客户端 API 的 PUT /api/v1/channels/{channelNo}，管理 token 用不了那个口。

设备

curl -sS "$BASE/api/v1/admin/devices" -H "Authorization: Bearer $TOKEN" \
  | jq '.devices[] | {device_id, name, group_id, last_seen_at, revoked_at}'

curl -sS -X DELETE "$BASE/api/v1/admin/devices/01J8ZK3Q7M2XW4V9HTNBSFY6PD" \
  -H "Authorization: Bearer $TOKEN"
  • GET /devices 跨所有 Space，每项：device_id、name、platform、group_id、created_at、last_seen_at、revoked_at。
  • 没吊销过的设备没有 revoked_at 这个键；响应里也不含任何密钥、token 或公钥。
  • 吊销不可逆：该设备 token 即刻失效、在线连接当场被踢，同一 Space 的其余端会收到一条设备已吊销的通知帧。要回来只能重新注册或输恢复码。
  • 设备号不存在 → 404，hint 为空串。
  • 每个 Space 的设备上限（pb.devices.max-per-group，默认 5）是在注册侧卡的，这一组接口只能看不能改。

消息搜索

只读，跨 Space。路径就是 /messages，没有 /search 那一段。

curl -sS -G "$BASE/api/v1/admin/messages" \
  -H "Authorization: Bearer $TOKEN" \
  --data-urlencode 'q=构建失败' \
  --data-urlencode 'channel_no=12345678' \
  --data-urlencode 'type=markdown' \
  --data-urlencode 'since=1760000000000' \
  --data-urlencode 'limit=200' | jq '.count, .messages[0]'
查询参数必填说明
q必填关键词，非空且不超过 100 个字符；命中正文、标题、摘要三者之一
channel_no可选精确频道号
type可选text / markdown / link / file
since可选，默认 0epoch 毫秒下限，只回这之后的消息
limit可选，默认 50取值 1~200；传 500 按 200 执行
  • q 的长度按字符数算，不是字节：101 个汉字会 400，60 个 emoji 不会。
  • q 前后空白会被去掉，纯空白按"必填"处理，回 400 hint:"q 不能为空"；超长度回 hint:"q 最长 100 字符"。
  • %、_、\ 是字面量，不会被当通配符：搜 100% 找的就是 100%。
  • type 是查询参数名，响应里对应字段叫 msg_type，照这个写。

响应是 {ok, count, messages}，按 seq 倒序（新→旧）。下面这份样本有 14 个键，但别按固定键数写解析——没值的键整个不出现，一条没填标题的消息只有 13 个键。

{
  "seq": 1042,
  "msg_id": "01J8ZK3Q7M2XW4V9HTNBSFY6PC",
  "channel_no": "12345678",
  "channel_name": "Grafana 告警",
  "group_id": "01J8ZK3Q7M2XW4V9HTNBSFY6PA",
  "sender_id": "ci",
  "sender_name": "构建机",
  "msg_type": "markdown",
  "title": "unit-test 失败",
  "summary": "order-svc 单测 3 个用例失败",
  "body": "### unit-test 失败\n…",
  "level": "error",
  "media_status": "ready",
  "created_at": 1760000000000
}

没有分页游标

一次最多 200 条，想看得更多只能缩小时间窗或换关键词。

它也不走全文索引，是大范围扫描。库里的消息到几十万行以后这个接口会明显变慢——它是给"运维查一条"用的，看趋势请走 概览统计。

概览统计

curl -sS "$BASE/api/v1/admin/overview" -H "Authorization: Bearer $TOKEN" | jq
{
  "ok": true,
  "stats": {
    "total_channels": 7, "active_channels": 6,
    "total_devices": 4, "active_devices": 3,
    "live_messages": 51234, "messages_today": 187
  },
  "trend": [
    { "day": "2026-10-07", "count": 233 },
    { "day": "2026-10-08", "count": 401 }
  ]
}
  • *_channels 的 active = 未归档；*_devices 的 active = 未吊销；live_messages = 未被删除的行。
  • messages_today 的"今天"按服务端所在机器的时区零点起算，不是 UTC。
  • trend 覆盖最近 14 天，day 按数据库时区格式化，逐日升序。
  • 零消息的那几天不出现在数组里：刚建起来的库可能数组长度只有 2。画图要么自己补零，要么接受断档。

定时推送

在服务端建任务：选频道、写正文、给 cron，服务端按时把消息灌进去。它走的是和外部 POST /message 完全同一条链路，发送者身份也是任务自己的：sender_id 省略或留空时按 "scheduled" 落库，填了就用填的那个，客户端据此把消息归到对应发送者的会话里；senderAvatar 是头像来源地址，触发时由服务端转存。

  1. 把任务写成 task.json 
    {
  "channelNo": "12345678",
  "name": "每晚巡检提醒",
  "category": "巡检",
  "title": "该跑 nightly-check 了",
  "content": "### 巡检\n1. 磁盘\n2. 证书",
  "level": "info",
  "senderId": "nightly-bot",
  "senderName": "值守机器人",
  "senderAvatar": "https://example.com/bot.png",
  "images": ["https://example.com/chart.png"],
  "cronExpr": "0 0 9 * * 1-5\n0 0 12 * * 0,6",
  "timezone": "Asia/Shanghai",
  "enabled": 1
}
    cronExpr 每行一条，6 段：秒 分 时 日 月 周，不认 5 段 unix cron。"每天 21:30" 写 0 30 21 * * *。多行就是一条任务挂多套作息：上面这个例子工作日 09:00、周末 12:00 各发一次，最多 8 行，空行会被忽略。
  2. 先预览，再落库 
    curl -sS -X POST "$BASE/api/v1/admin/scheduled-tasks/preview" \
  -H "Authorization: Bearer $TOKEN" -H 'Content-Type: application/json' \
  --data-binary @task.json | jq .preview
    请求体与建任务同一份，只渲染、不落库：content 是变量替换后的正文，bytes 对上 max_body_bytes，超了只把 over_limit 标成 true，这里不报 400——真正拦人的闸在保存那一步。next_fires 逐条列出每条 cron 的下次触发，next_fire_at 是所有规则里最近的那一次。
  3. 提交 
    curl -sS -X POST "$BASE/api/v1/admin/scheduled-tasks" \
  -H "Authorization: Bearer $TOKEN" -H 'Content-Type: application/json' \
  --data-binary @task.json | jq .task
    期望 200，task.enabled 是 1，task.next_fire_at 是未来某个时刻的毫秒时间戳。
  4. 看它到底发出去了没 
    curl -sS "$BASE/api/v1/admin/scheduled-tasks/<task_id>" \
  -H "Authorization: Bearer $TOKEN" | jq '.task | {last_result, last_msg_id, last_fire_at}'
    跑成功后 last_result 是 "ok"，last_msg_id 可以拿去 消息搜索 里核对。
  5. 启停与删除 
    curl -sS -X POST "$BASE/api/v1/admin/scheduled-tasks/<task_id>/enabled" \
  -H "Authorization: Bearer $TOKEN" -H 'Content-Type: application/json' \
  --data-binary '{"enabled":0}' | jq '.task.enabled'

curl -sS -X DELETE "$BASE/api/v1/admin/scheduled-tasks/<task_id>" \
  -H "Authorization: Bearer $TOKEN"
    只有 1 算启用，其余值一律当停用。停用期间不会发，也不会补跑；重新启用时 next_fire_at 从当下往后算。

请求体字段（驼峰）

字段必填说明
channelNo必填目标频道；不存在 404，已归档 400
content必填正文，UTF-8 字节数不得超过该频道的 max_body_bytes（默认 32768）。支持 ${now} / ${now:yyyy-MM-dd HH:mm} / ${scheduled_at} 等变量，认不出的原样保留
cronExpr必填每行一条 6 段 cron，最多 8 条，触发取所有行里最近的一次；段数或取值非法、超过 8 条、或全部已经没有下一次，都是 400（多行时错误里带「第 N 条」）
timezone可选IANA 时区名（Asia/Shanghai、UTC…），省略按 Asia/Shanghai 落库；cron 与正文里的时间变量都按它算，非法值 400
level可选info / warning / error；写错会安静变成 info，不报错
name / title / senderName可选去空白后分别最长 64 / 512 / 64 字符
senderId可选发送者标识，最长 64 字符；省略、留空或全空白按 scheduled 落库，超长截断。它决定客户端把消息归到哪个发送者会话，与外部 POST /message 的 sender_id 是同一个字段
senderAvatar可选头像来源 URL，最长 1024 字符、只允许 http / https；data: 内联头像超长，会被 400 拒绝（先传到图床）。触发时由服务端转存，客户端再通过 /api/v1/avatars/{token} 取
category可选列表用的自由标签，最长 32 字符，不校验取值
images可选外链数组，最多 4 条、单条不超过 1024 字符，只允许 http / https
enabled可选省略即 1（启用）

响应字段（下划线）

字段出现在说明
task_id、group_id、channel_no、name、category、title、level、sender_id、sender_name、sender_avatar、cron_expr、enabled、created_at、updated_at列表、详情、写操作都有enabled 是 0/1 数字；没填的字符串字段回 ""，不会缺键。sender_id 恒有值（老任务是 "scheduled"），sender_avatar 没设时回 ""，两者都决定触发时那条消息的发送者身份
channel_name只有列表详情和三个写操作的响应里都没有这个键
content_head列表和写操作正文前 80 个字符，这两种形状故意不回全文
content、images只有详情要完整载荷就读详情；详情里没有 content_head
next_fire_at、last_fire_at、created_at、updated_at都有（next_fires 只有预览）epoch 毫秒；没值回 0，不是 null，键也不会消失。多行 cron 时 next_fire_at 是最近的那一次，逐条时刻看预览响应的 next_fires[]
last_result、last_error、last_msg_id跑过之后才有从没跑过的任务里这三个键都不存在；哪个出现由下面那条说明决定

last_* 三个键的组合会随执行结果变，用它们对账时两件事一起判：

  • 跑成功那一轮：出现 last_result:"ok" 和 last_msg_id，last_error 缺席。
  • 跑失败那一轮：出现 last_result:"failed" 和 last_error，last_msg_id 反而被清掉。
  • 所以 last_msg_id 是"最后一次尝试产生的消息 id"，不是"最后一条成功送达的消息"；last_error 最长 255 字符。

改一条任务

PUT 是整体覆盖，不是补丁

没在请求体里出现的字段会被清成默认值：name、title、senderName 变 ""，senderId 回落到 "scheduled"，senderAvatar 变 ""，images 变空数组，level 回落到 info。漏一个就静默清空一个。

  1. 先把详情整个读下来 
    curl -sS "$BASE/api/v1/admin/scheduled-tasks/<task_id>" \
  -H "Authorization: Bearer $TOKEN" | jq '.task' > task.json
  2. 把下划线键改成驼峰，只动你要改的值 
    jq '{channelNo:.channel_no, name, category, title, content, level,
      senderId:.sender_id, senderName:.sender_name, senderAvatar:.sender_avatar,
      images, cronExpr:.cron_expr, enabled}' task.json > put.json
    详情读回来的键是下划线，PUT 要的键是驼峰，中间这一步不能省。
  3. 覆盖回去 
    curl -sS -X PUT "$BASE/api/v1/admin/scheduled-tasks/<task_id>" \
  -H "Authorization: Bearer $TOKEN" -H 'Content-Type: application/json' \
  --data-binary @put.json | jq '.task | {cron_expr, next_fire_at}'
    改了 cronExpr 就按新表达式从当下重算 next_fire_at；已跑过的 last_* 结果原样保留。

执行口径

  • 多条 cron 是一条任务，不是多条任务。所有行共用同一份正文、时区与启停状态；哪一行先到就按那一刻发，撞在同一秒也只发一条（时隙幂等键按任务算，不按行算）。
  • 精度到分钟，不到秒。亚分钟级的 cron 会被推迟到下一个扫描点，实际效果是每分钟最多一条；0/5 * * * * * 不会每 5 秒发一条。
  • 扫描周期 pb.scheduled.sweep-interval（默认 15 秒），每轮最多处理 pb.scheduled.batch-size（默认 50）条。
  • 宕机几小时后只补当前这一次，不逐分钟回补，之后回到正常节律。
  • 投递失败会记下 last_result:"failed" 和 last_error，但不会停任务，下个时隙还会再失败一次。
  • 唯一的例外：目标频道中途被归档，下一轮会把任务 enabled 直接置成 0，last_error 是「频道已归档或不存在，任务已自动停用」。
  • 任务的归属 Space 是从目标频道反查的，不用调用方给。
  • 发出去的消息用任务自己的发送者身份：sender_id 决定客户端把消息归到哪个会话，sender_avatar 在触发时由服务端转存（同一发送者只保留最新一张）；这是消息里的一份展示身份，不占设备的自报名。
  • DELETE 是真删任务，已经发出去的消息不受影响。

一次完整的运维流程

从登录到建频道、验证入站、挂上每晚提醒，一份能直接跑的脚本。依赖 curl 与 jq。

#!/usr/bin/env bash
set -euo pipefail
BASE="${PB_BASE:?例 http://127.0.0.1:7404}"
ADMIN_PASSWORD="${ADMIN_PASSWORD:?安装页里填的那个管理台口令}"

# 1) 口令换 token
TOKEN=$(curl -sS -X POST "$BASE/api/v1/admin/login" \
  -H 'Content-Type: application/json' \
  --data-binary "$(jq -nc --arg s "$ADMIN_PASSWORD" '{secret:$s}')" | jq -er .token)

# 2) 从设备列表挑一个 group_id 作为目标 Space
GROUP=$(curl -sS "$BASE/api/v1/admin/devices" -H "Authorization: Bearer $TOKEN" \
  | jq -er '.devices[] | select(.revoked_at==null) | .group_id' | head -1)

# 3) 建频道，频道号与密钥落到文件，不进终端历史
curl -sS -X POST "$BASE/api/v1/admin/channels" -H "Authorization: Bearer $TOKEN" \
  -H 'Content-Type: application/json' \
  --data-binary "$(jq -nc --arg g "$GROUP" '{groupId:$g,name:"nightly",maxLevel:"error",maxImages":4}')" \
  | jq -r '[.channel_no,.secret] | @tsv' > channel.tsv

# 4) 从第三方那侧的入站口发一条，验证整条链路
read -r NO SECRET < channel.tsv
curl -sS -X POST "$BASE/message" -H 'Content-Type: application/json' \
  --data-binary "$(jq -nc --arg c "$NO" --arg s "$SECRET" \
    '{channel:$c,secret:$s,content:"链路自测",level:"error",sender_id:"ops"}')"

# 5) 搜到它，确认已经落库
curl -sS -G "$BASE/api/v1/admin/messages" -H "Authorization: Bearer $TOKEN" \
  --data-urlencode 'q=链路自测' | jq '.count, .messages[0].msg_id'

# 6) 挂一个每晚 21:30 的任务
curl -sS -X POST "$BASE/api/v1/admin/scheduled-tasks" -H "Authorization: Bearer $TOKEN" \
  -H 'Content-Type: application/json' \
  --data-binary "$(jq -nc --arg c "$NO" \
    '{channelNo:$c,name:"每晚提醒",title:"该跑巡检了",content:"见 cron",level:"info",cronExpr:"0 30 21 * * *"}') \
  | jq -r '.task.task_id, (.task.next_fire_at|tostring)'
  • 口令与请求体一律用 jq -n 现拼，密钥不写进脚本正文。
  • groupId 从真实设备反查，避免建出设备永远看不见的频道。
  • 第 5 步的 count 是 1 才算链路通；第 6 步回一个任务号和一个未来的毫秒时间戳才算排上。

用之前要知道的四件事

  • 权限是全局的，没有分级。没有只读 token，也没有限定某个 Space 的 token，同样没有审计日志。
  • 这一组接口默认公网可达。全部防线就是那一条口令加 24 小时的 token。要按来源网段收口，得自己在前置的 Nginx / 防火墙加规则。
  • 除登录锁定外没有独立限流。滥用防线只有"token 得先拿到"这一条。
  • 建频道与重置密钥没有控制台按钮，只有 API 形态；正常建频道是在设备上做的。这两个端点是给脚本和救急留的。
发进去看不到效果？按顺序排三件事：入站 API 查凭据与限流，本页 消息搜索 确认落库，客户端 API 的增量拉取确认设备上读不读得到。三套鉴权互不相通，卡在哪一层就查哪一层。
