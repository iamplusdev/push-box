# PushBox Docker 部署快速参考

> 服务端**不需要任何环境变量**：镜像里没有配置类 `ENV`，没有必填变量，没有 `__SET_ME__` 占位值。
> 库地址与口令、对象存储、加密口令、管理台口令、端口、运维网段、图片抓取放行主机，全部在**首次启动弹出的安装页**里填，
> 落盘成 `/app/data/config/pushbox.json`，那一份就是唯一的配置落点。
>
> "不需要"不等于"给了也不认"：`PB_*` 仍走 Spring 的宽松绑定，且优先级**高于**这份 JSON
> （`RuntimeConfigEnvironmentPostProcessor` 的顺序是 `环境变量 > 本文件 > yml`，命令行与 `-D` 再压过环境变量）。
> 探针、体检与"临时改一个值别动文件"靠的就是这一层。

---

## 🚀 主路径：一个容器，零个变量

这一条**不用克隆仓库、不用 `.env`，也不用给任何 `-e`**：

```bash
docker run -d --name pushbox \
  -p 7404:7404 \
  -v pushbox_data:/app/data \
  docker.io/iamplusdev/push-box:latest   # 或钉本次的版本号，两者是同一份镜像
```

然后浏览器打开 http://127.0.0.1:7404/ ——看到的就是安装页。

之所以不再走环境变量：NAS 的「创建容器」表单只能逐行填 ENV，于是"要填几项"变成了十几个键名与占位值的
组合，填错任何一项的表现都是**容器起来了但半死**；而一个网页表单能把"库连不上"这种错当场说清楚，
还能顺手把库建出来。

`docker.io/iamplusdev/push-box` 这一个镜像里同时有 API、WebSocket、入站端点和 Web 管理台：
`infra/Dockerfile` 的 node 阶段把 `apps/web-admin` 打进 jar 的 `classpath:/static/`，由同一个 Spring Boot
进程在同一个端口吐出来——**没有第二个前端容器，也不需要额外反代规则与 CORS 配置**。
装完之后管理台在**根路径 `/`**（不是 `/admin`，SPA 没配 vite base），打开就是登录页。

### 安装页是怎么工作的

没有配置文件时，`main()` 先用 JDK 自带的 HttpServer 在服务端将要用的那个端口（默认 7404）上起一个
迷你服务：根路径 `/` 是表单，提交走 `POST /api/v1/setup`。提交时它按顺序做三件事：

1. **全量校验表单**（格式层，不碰网络）：端口 1–65535；库五项都要填；勾了对象存储则地址、桶名、
   AK/SK 必填；勾了加密则口令与主钥**二选一必填**；管理台口令要么留空、要么至少 8 个字符；
   运维网段每一项都得是 CIDR（含 `/`）；图片抓取放行主机每一项都得是裸 `host` 或 `host:port`
   （不带 scheme、不带路径、不带通配——`SsrfGuard` 是精确等值比较，写成 `http://img.lan` 或 `*.lan` 等于没填）。
2. **真连一次库**：连上之后执行 `CREATE DATABASE IF NOT EXISTS pushbox`（utf8mb4 / `utf8mb4_0900_ai_ci`），
   建不动不算失败，下一步直连那个库时会给出真原因。
3. 勾了对象存储的话**真连一次桶**：headBucket + putObject + deleteObject 各来一次，
   端口或凭据填错在保存之前就会被拦下来。

任何一项不过就**一个字节都不写盘**，并把具体原因回给你——所以"配了一半"这种状态不存在：
要么这份配置能跑，要么它根本没落盘。全过之后配置写进 `/app/data/config/pushbox.json`
（原子写：先写同目录临时文件再 move；权限 `rw-------`），**同一个 JVM 接着往下启动 Spring，
不需要重启容器**。文件一落盘安装页就停了，之后重启也不会再看到它。

页面上还有两个辅助动作：

- **「测试连接」**（`POST /api/v1/setup?action=test`）：只测库，让你在提交整份配置之前先看到
  "这个地址/口令对不对"。
- **「从库里找回上一次的配置」**（`?action=restore`）：服务端启动后会把整份配置抄一份进库
  （`app_state.runtime_config_v1`），重装或换机器时只带库凭据过来，就能把上次的整份 JSON 拉回来改，
  不用重填一遍。

**明文凭据是刻意的**：`pushbox.json` 里明文存着库口令、桶 AK/SK、管理台口令与加密口令。
理由写在 `RuntimeConfig` 的注释里：生产部署一定要有可复核的凭据落点，"只从环境变量读"换来的是一堆
占位值和一个拒绝启动的入口脚本，部署者仍然要把真值写在某个文件里（compose 的 environment、NAS 的表单），
只是那个文件没人管权限。现在落点收敛成一个文件，权限也只用管这一个。**这份文件（或整个 `/app/data` 卷）
要跟着数据库一起备份**——见下面「明文配置与备份」。

### 镜像之外只有一件事：库账号要先存在

**库和表都不用你建**：库由安装页执行 `CREATE DATABASE IF NOT EXISTS` 建出来，表由 Flyway 首次启动建
（首启要建九张表，慢个几十秒到一两分钟是正常的）。但**数据库用户和授权要你自己先建好**，
在库所在那台机器上跑一次就够：

```sql
CREATE USER IF NOT EXISTS 'pushbox'@'%' IDENTIFIED BY '<强口令>';   -- 必须是 '%'：另一个容器连过来的来源不是 localhost
GRANT SELECT, INSERT, UPDATE, DELETE, CREATE, ALTER, INDEX, DROP, REFERENCES
  ON pushbox.* TO 'pushbox'@'%';
FLUSH PRIVILEGES;

SELECT @@ngram_token_size;   -- 期望 2；不是 2 就搜不出中文长句
```

安装页里「数据库地址」填库所在机器的局域网 IP 或服务名，**别填 `127.0.0.1`**——容器里的环回是它自己，
填了它安装页会当场把这句话告诉你（`InstallServer` 的报错自带这条提示）。

两条边界别等起完容器才发现：

- **库只能是 MySQL 8.0 / 8.4**。`V1__init.sql` 用了 `utf8mb4_0900_ai_ci` 与 `FULLTEXT … WITH PARSER ngram`，
  MariaDB 与 MySQL 5.7 过不去。
- **Hub 上那份镜像只有 linux/amd64**（发布工作流没传 `platforms`）。ARM 机型要自己构建：
  `docker build -f infra/Dockerfile -t pushbox:local .`——这一步才需要克隆仓库，因为它读的是仓库里的 `Dockerfile`。

### 安装页上有哪些项（对应 pushbox.json 的字段）

| 分组 | 字段 | 默认 | 说明 |
|------|------|------|------|
| 数据库 | `database.host` / `port` / `name` / `username` / `password` | `127.0.0.1` / `3306` / `pushbox` / `pushbox` / 空 | 五段分开填，JDBC URL 由服务端拼（那一整条串是最容易填错的一项）。容器部署时 host 必须改 |
| 存储 | `storage.s3`（开关） | `false` | 关 = 本地目录，图片落 `/app/data/media`，零依赖；开 = 下面几项必填 |
| 存储 | `storage.endpoint` / `region` / `bucket` / `accessKey` / `secretKey` | 空 / `us-east-1` / `pushbox` / 空 / 空 | 勾了对象存储就都要填。**桶要先自己建**（见下面「桶要建一次」） |
| 存储 | `storage.pathStyle` | `true` | MinIO / RustFS 用 `true` 是对的；阿里云 OSS 或 AWS 按服务商文档可能要关 |
| 存储 | `storage.encrypted`（开关）+ `storage.passphrase` | `false` / 空 | 开 = 每对象客户钥（SSE-C），口令由 Argon2id 派生出 KEK，至少 12 个字符（按 Unicode 码点数） |
| 存储 | `storage.masterKey`（高级项） | 空 | base64 的 32 字节（`openssl rand -base64 32`），与口令**二选一**，同时填安装页会拒绝——两者派生出的密钥不同，无法判断该用哪一把 |
| 存储 | `media.allowHosts` | `[]` | 图片**从哪抓**的豁免名单：抓取器默认拒绝一切回环 / 私网 / CGNAT 地址（防 SSRF），图床在内网时必须在这里点名。裸 `host` 或 `host:port`，**精确等值**，无通配。漏填的表现是每条图片都 `media_objects.error=ssrf_blocked`，客户端只看到图不见了 |
| 管理台 | `admin.password` | 空 | **留空 = 管理台整个关闭**（`/api/v1/admin/*` 一律 403「管理台未启用」，收发不受影响，这是安全状态不是漏配）。要开就填至少 8 个字符 |
| 管理台 | `admin.jwtKey` | 空 | **不用你填**：服务端首次启动自动生成（随机 32 字节 base64）并回写配置文件。旧的"两个密钥、必须不同、各自 ≥32 字节"那套要求随之作废 |
| 运维 | `security.internalCidrs` | `[]` | `/healthz` 与 `/actuator/**` 的额外放行网段（CIDR 数组），环回永远放行。留空 = 只有容器自己能读 |
| 其它 | `port` | `7404` | 容器内**通常别改**，理由见「端口」一节 |

### 三条不能省的

- **`/app/data` 那一个卷要挂**。镜像只声明一个 `VOLUME ["/app/data"]`，配置（`config/`）、图片（`media/`）、
  日志（`logs/`）全在这一个目录里；不挂等于写在容器可写层，`docker rm` 之后全没——**包括安装页填的那些值**。
- **`/app/data` 归 uid 10001**。镜像里的运行用户是 `pushbox(10001)`，entrypoint 现在只剩一件事：
  `/app/data` 的写入探针。绑定挂载会把宿主目录的属主带进来，宿主目录不是它可写时，探针当场拒绝启动
  并给出两种修法（改用 named volume，或 `sudo chown -R 10001:10001 <宿主目录>`）。
- **容器内端口固定 7404，要换端口换宿主侧映射**（`-p` 的左侧）。见下面「端口」一节。

### 验收：在容器里取，不要在宿主上取

```bash
docker exec pushbox curl -s http://127.0.0.1:7404/healthz
# 期望最后一段：{"ok":true,"db":"up","storage":"up","uptime_ms":…}
```

**别在宿主上 `curl http://localhost:7404/healthz`**：`InternalAccessFilter` 只认 `getRemoteAddr()`，
经端口映射进来的连接在容器里看到的是网桥网关而不是 127.0.0.1，会被回 **404**（拒绝时故意不用 403，
免得扫描器确认这里有个运维端点）。这不是故障；要从宿主或监控直接读，把这套网络分到的子网填进
安装页的「运维网段」（`security.internalCidrs`）。容器状态 `healthy` 也只代表 TCP 探活通了，
不等于 `db=up`——healthcheck 是纯 TCP 的（`exec 3<>/dev/tcp/127.0.0.1/7404`），这是刻意的：
`/healthz` 会真连库，用业务探活做 healthcheck 等于让一次数据库抖动就把容器判死；而且没配置完的容器
停在安装页上，那时 `/healthz` 根本不存在，但 7404 已经有人监听。
镜像里有 `curl`（`eclipse-temurin:21-jre` 自带），没有 mysql 客户端——原因见下面「健康检查 db=down」。

### 在 NAS 的图形界面里装（飞牛 / 群晖 / 1Panel）

走 **[NAS部署指南.md](NAS部署指南.md)**，或直接贴 **[docker-compose.nas.yml](docker-compose.nas.yml)**
（那本文件整本零插值，一个变量都没有，改一行端口映射就能 `up`）。
「创建容器」表单那种装法同样成立：镜像声明了唯一一个 `VOLUME /app/data`，「存储位置」只有**一行**要选
——把它指到 NAS 的共享文件夹，配置、图片、日志就都保住了；**环境变量那一栏一行都不用填**。
要填的东西全在安装页里，`up` 之后浏览器打开 `http://<NAS_IP>:7404/` 就是。

### 端口

7404 在容器内是写死的，落在四个地方：`application.yml`、`Caddyfile` 的上游、compose 的 `ports`、
compose 的 `healthcheck`。在安装页里改 `port` 就要把这四处一起改，少改一处就是"容器起了但反代 502 /
没人监听映射端口"的怪事——所以口径是**容器里别改端口，要改改宿主侧映射**：
主路径改 `-p <宿主端口>:7404` 的左侧，compose 形态改 `.env` 里的 `PB_HTTP_PORT`（Caddy 对外端口，默认 80）。

## 🐳 形态二：compose（要反代 / 监控 / 自带库和桶时才走）

**为什么这一条要 `git clone` 而主路径不用**：`docker-compose.yml`、`Caddyfile`、
`docker-compose.monitoring.yml` 和那几段 sidecar 定义都是**文件**，它们装不进 `pushbox` 镜像里；
`.env` 只是给这些文件记账的那一层。只要一个容器时用不到它们。要 Caddy 反代、要 Prometheus/Grafana，
或者想让 compose 顺手把 MySQL 与 RustFS 一起起来，才需要这一节。

**`.env` 现在只装两类东西**（见 `infra/env/prod.env.example` 顶部说明）：

1. 第三方镜像自己的凭据（mysql / rustfs / grafana）——它们只认环境变量，服务端一个都不读；
2. 宿主侧的端口与域名（`PB_CADDY_HOST` / `PB_HTTP_PORT`），不进容器。

拓扑 A（复用外部已有的库与桶）+ 不开监控的话，`.env` 里**必填的只有 `PB_CADDY_HOST` 一项**。
注意 `PB_DB_PASSWORD` / `PB_S3_ACCESS_KEY` / `PB_S3_SECRET_KEY` 仍在模板里，但它们**只喂 compose 里
那段可选的 mysql / rustfs 第三方镜像**——安装页里要填同一个值，两处同值（compose 没法在一个文件里
引用自己写过的值，这是这套写法的代价）。

拓扑三选一，区别只在安装页里怎么填，compose 文件本身一个字都不用改。

### 拓扑 A：复用已有的 MySQL 与桶（推荐生产环境）

```bash
# 1. 克隆并进入部署目录
git clone https://github.com/iamplusdev/push-box.git
cd push-box/infra

# 2. 准备 .env，改域名（拓扑 A 只有这一项必填）
cp env/prod.env.example .env
# vi .env  # PB_CADDY_HOST=你的域名

# 3. 启动服务（服务端 + Caddy）
docker compose up -d

# 4. 浏览器打开 http://<PB_CADDY_HOST>/ 或 http://127.0.0.1:7404/ ——安装页也走同一条反代，
#    不需要额外的端口或路径规则。填表、提交，同一个容器接着起服务。
#    库地址填那台 MySQL 的 IP（⚠ 不是 127.0.0.1，容器里的环回是它自己）；
#    勾上对象存储就把地址指到那个桶（端口跟着实例走，见「桶要建一次」里 9000/7101 那条）。

# 5. 等就绪（首次要跑 Flyway 建表，日志里出现 Started PushboxServerApplication 就够了）
docker compose logs -f pushbox-server    # Ctrl-C 退出

# 6. 验收：这一套把 7404 只绑宿主环回（127.0.0.1:7404:7404），手机/PC 直连 :7404 是连不通的——
#    那是设计，不是故障。/healthz 要在容器里取（从宿主打过去是 404，见「验收」）：
docker compose exec pushbox-server curl -s http://127.0.0.1:7404/healthz
```

Caddy 的 `depends_on: service_healthy` 不会被安装页卡住：healthcheck 判的是**端口通不通**（纯 TCP），
不是 `/healthz`。Caddy 对 `/actuator/*` 一律回 403，管理台默认和业务 API 一样公网可达——
想收紧按 `infra/Caddyfile` 里那段注释示例改。

要监控栈就多带一本文件（Prometheus + Grafana 都在里面，只绑 127.0.0.1）：

```bash
docker compose -f docker-compose.yml -f docker-compose.monitoring.yml up -d
```

**开监控必须把这条网络分到的子网填进「运维网段」**，否则进程好好的、targets 全 403：

```bash
docker network inspect pushbox_default -f '{{range .IPAM.Config}}{{.Subnet}}{{end}}'
```

填法：改配置文件里的 `security.internalCidrs` 再重启，或删掉 `data/config/pushbox.json` 回到安装页重填
（用「从库里找回上一次的配置」捞回来改，不用重填一遍）。监控那本文件还要 `.env` 里的
`GRAFANA_ADMIN_PASSWORD`（grafana 镜像只认环境变量）。

### 拓扑 B：库和桶也让 compose 一起起来

取消 `docker-compose.yml` 里 `mysql` / `rustfs` 那两段的注释，`.env` 里补上
`MYSQL_ROOT_PASSWORD` / `PB_DB_PASSWORD` / `PB_S3_ACCESS_KEY` / `PB_S3_SECRET_KEY`
——**这些值喂的是那两个第三方镜像**：mysql 镜像拿 `PB_DB_PASSWORD` 建用户，rustfs 镜像拿
`PB_S3_ACCESS_KEY` / `PB_S3_SECRET_KEY` 建账号。**安装页里要填同一个值**：库地址填服务名 `mysql`、
口令填 `.env` 里 `PB_DB_PASSWORD` 那个值；对象存储地址填 `http://rustfs:9000`
（`rustfs/rustfs:latest` 监听 9000(S3)/9001(Console)），AK/SK 填 `.env` 里那两项的同值。
同一网络内用服务名，不要填宿主 IP。

**建账号这一步照样在你自己身上**：mysql 那段起来的是空实例（`MYSQL_DATABASE` 会建库，但
`'pushbox'@'%'` 用户与授权仍按上面那段 SQL 来）；**桶也不会自动出现**，先建一次（见「桶要建一次」），
否则安装页提交时那一步 putObject 会直接报回来。嫌手写麻烦可以直接用 `docker-compose-wsl.yml` +
`deploy-wsl.sh`：`up` 起栈（容器停在安装页上）、`bucket` 建桶、`setup` 把 `wsl-test.env` 里的测试值
POST 给 `/api/v1/setup`——走的是和真人点「保存并启动」完全相同的一条路。

空库首次初始化在 NAS 上普遍要 1～2 分钟：这期间安装页的「测试连接」会报连不上，
用 `docker logs <mysql 容器名> --tail 20` 看它到哪一步了，起好再回来点一次。

### 拓扑 C：不用桶（本地文件存储）

安装页里**不勾「改用对象存储」**就行：图片与头像落在同一个卷的 `media/` 下
（容器里是 `/app/data/media`，`storage.localPath` 默认 `data/media`，相对工作目录 `/app`）。
无需部署 MinIO/RustFS，适合个人或小团队轻量级部署；MySQL 仍然要有。

对象的去向要说清楚，因为它决定备份怎么做：compose 把 `/app/data` 挂在一个 **named volume** 上
（项目名 `pushbox` + 卷名 `pushbox_data`，即 `pushbox_pushbox_data`），不是宿主目录。原因是绑定挂载会把
宿主目录的属主带进容器，而 Docker 替缺目录建出来的宿主目录属 root，容器里的 `pushbox(10001)` 写不动；
named volume 首挂时继承镜像里那个目录的属主，所以 `up` 完就能写。

想改成看得见的路径（方便直接 `tar`）就把 volumes 那行换成 `- ./data:/app/data`，
代价是先把宿主目录交给运行用户：`sudo mkdir -p ./data && sudo chown -R 10001:10001 ./data`。
两种挂法都会先过 entrypoint 的写入探针，探不过就拒绝启动并把上面这两种修法打出来。

```bash
# 查数据实际落在哪（named volume 的挂载点；备份脚本的 MEDIA_DIR 指它下面的 media/ 子目录）
docker volume ls | grep pushbox                                   # 先认卷名，它跟着起法走
docker volume inspect <上面那个卷名> -f '{{.Mountpoint}}'
```

**卷名不是一个固定值**，`docker volume inspect` 报 `No such volume` 十有八九是名字抄错了：
`docker run -v pushbox_data:/app/data` 建的卷就叫 `pushbox_data`；compose 会加项目名前缀，
`docker-compose.yml`（`name: pushbox`）是 `pushbox_pushbox_data`，`docker-compose.nas.yml`
（`name: pushbox-nas`）是 `pushbox-nas_pushbox_data`。所以下面凡是写卷名的地方都先用
`docker volume ls | grep pushbox` 认一次。

### 加密口径（两个布尔，2026-10 起）

存储从旧的三档开关（`PB_STORAGE_TYPE` × `PB_S3_OBJECT_ENCRYPT` × 逃生阀）变成**两个布尔**：
勾不勾「改用对象存储」（`storage.s3`）、勾不勾「加密存储」（`storage.encrypted`）。
加密管的是**对象字节**，跟用不用对象存储服务无关：本地目录模式同样按这个开关决定落盘的是明文还是
`KeyWrap.seal` 封装后的密文，读侧按 `media_objects`/`senders` 各自记的 `enc_mode` 逐对象解读。

**"忘了配就等于拒绝启动"那道闸门没有了**：加密现在是表单上一个开关，勾不勾由你表态，
不再有 `PB_ALLOW_PLAINTEXT_MEDIA` 这种逃生阀。桶侧明文的代价自己掂量：任何拿到同一组 AK/SK 的读者
都能直接把图片读走；本地目录是自己这块盘，威胁模型不一样。

勾了「加密存储」，KEK 来源二选一：

| 项 | 规则 |
|------|------|
| `storage.passphrase`（推荐） | 至少 12 个字符（NFC 归一化后按 Unicode 码点数），由 Argon2id 派生出 KEK |
| `storage.masterKey` | base64 的 32 字节（`openssl rand -base64 32`），格式不对安装页当场拒 |
| 两个都填 | 安装页拒绝：「两者派生出的密钥不同，同时填无法判断该用哪一把」 |
| 都不填 | 安装页拒绝：「开启了存储加密，就要填一个加密口令（推荐）或一把主钥」 |

**KEK 一旦有对象落库就不可轮换**——换了口令或主钥等于旧封装钥全解不开，表现为图片集体消失且不可恢复。
这一条在表单上没法拦，只能写在这里。口令本身不存库：`app_state.media_kek_v1` 只存随机盐、KDF 参数与
校验值（KCV），所以**库还在、口令没变，重启/重装/重建容器都能派生出同一把 KEK、读回旧图**；
反过来口令忘了与主钥丢了等价。启动时 KCV 对不上会拒绝初始化 KEK（报「加密口令与首次启用时不是同一个」）；
库还没写过图片时，可手工删掉 `app_state` 里的 `media_kek_v1` 一行后用新口令重新初始化
（`MediaKeyService` 的报错自带这句修法）。

## 📋 配置文件速查（pushbox.json）

配置的唯一落点是 `<工作目录>/data/config/pushbox.json`，容器里就是 `/app/data/config/pushbox.json`
（权限 `rw-------`）。全字段模板见 [pushbox.json.example](pushbox.json.example)；
不想用安装页也可以直接写这份文件，位置用 `--pb.config-file=/path/to/pushbox.json`
（或 `-Dpb.config-file=...`）指定。字段与默认值以 `RuntimeConfig.java` 为准：

| 字段 | 默认值 | 备注 |
|------|--------|------|
| `port` | `7404` | 容器内别改，见「端口」 |
| `database.host` | `127.0.0.1` | 容器部署必须改成库那台机器的地址 |
| `database.port` / `name` / `username` | `3306` / `pushbox` / `pushbox` | 库名只能是字母、数字、下划线与 `$` |
| `database.password` | 空 | 必填；JDBC 串由服务端拼，不用手写 |
| `storage.s3` | `false` | 勾了则 endpoint / bucket / accessKey / secretKey 必填 |
| `storage.localPath` | `data/media` | 相对工作目录；容器里即 `/app/data/media` |
| `storage.endpoint` | 空 | 例 `http://192.0.2.10:9000` |
| `storage.region` / `bucket` / `pathStyle` | `us-east-1` / `pushbox` / `true` | pathStyle 对 MinIO/RustFS 是 `true`，OSS/AWS 按服务商文档 |
| `storage.encrypted` | `false` | 勾了则口令或主钥二选一必填 |
| `storage.passphrase` / `masterKey` | 空 / 空 | 见「加密口径」；**不可轮换** |
| `admin.password` | 空 | 空 = 管理台关闭；非空至少 8 个字符 |
| `admin.jwtKey` | 空 | 服务端自动生成并回写，永远不用手填 |
| `security.internalCidrs` | `[]` | CIDR 数组；空 = 只放行容器环回 |
| `media.allowHosts` | `[]` | 图片抓取的内网豁免主机（`host` 或 `host:port`，精确等值）；空 = 私网一律不抓 |

改配置的两条路：

- **直接改文件**：编辑卷里的 `config/pushbox.json` 再重启容器（`docker restart pushbox` /
  `docker compose restart pushbox-server`）。
- **回到安装页**：把那个文件删掉（`docker compose exec pushbox-server rm /app/data/config/pushbox.json`），
  下次启动就回到安装页，用「从库里找回上一次的配置」把原来那份捞回来改。

两条路都**换不了 KEK**（`storage.passphrase` / `storage.masterKey`）：有对象落库之后就不可轮换。
换 `admin.jwtKey` 是另一回事——它会让所有已登录会话当场失效，需要重新登录；换 `admin.password` 不会。

`storage.endpoint` 的端口跟着实例走，别互相抄：`rustfs/rustfs:latest` 镜像监听 **9000**（S3）/ 9001（Console），
而 §11.1 那台远端存储机把实例挂在 **7101**。现在填错端口在保存之前就会被安装页的连通性检查拦下；
但装完之后 `/healthz` 的 `storage` 仍只判配置非空、不探测可达性（`HealthzController.storageConfigValid`），
所以事后改错地址会一路绿灯，直到第一条带图的消息在抓取阶段停在 `failed` 才看得见；
本地存储那一路是真去写一个探针文件，写不动就报 `storage=down`。

## 🪣 桶要建一次（用对象存储时）

服务端不会自动建桶（代码里没有 CreateBucket），仓库里也没有任何 provisioning 步骤；
安装页的连通性检查会真往桶里写一个对象再删掉，所以**桶必须在提交配置之前就存在**。
用 `mc`（或 RustFS 控制台）建一次，取值就是你在安装页里填的那几项：

```bash
mc alias set pb "http://<S3_HOST>:9000" "<AccessKey>" "<SecretKey>"
mc mb --ignore-existing "pb/pushbox"
mc ls pb            # 能看到桶才算这一步过了
```

**手上没有 `mc` 就别去现找**：2026-10-20 实测 `minio/mc` 与 `minio/minio` 在 Docker Hub 都已取不到
（`hub.docker.com/v2/repositories/minio/mc` → 404），`dl.min.io/client/mc/release/linux-amd64/mc` → **410 Gone**。
CI 以前就是拉 `minio/mc` 建桶的，现在改用 AWS CLI v2（Linux 安装包 `https://awscli.amazonaws.com/awscli-exe-linux-x86_64.zip`，实测 200）。等价命令：

```bash
export AWS_ACCESS_KEY_ID='<AccessKey>' AWS_SECRET_ACCESS_KEY='<SecretKey>' \
       AWS_DEFAULT_REGION=us-east-1
# region 只是 SigV4 的签名字段，RustFS 不看它；裸 IP 的 endpoint 会自动走 path-style。
aws --endpoint-url "http://<S3_HOST>:9000" s3api create-bucket --bucket pushbox
aws --endpoint-url "http://<S3_HOST>:9000" s3api head-bucket --bucket pushbox   # 退 0 才算过
```

这两条 2026-10-20 在本地对真 `rustfs/rustfs:latest` 容器实测过：`create-bucket` 退 0、重复执行不报错、`head-bucket` 确认桶在。

桶在 compose 自带的 rustfs 里（拓扑 B）时，`docker-compose-wsl.yml` 不给 rustfs 发布端口，
客户端要借它自己的网络命名空间才够得着 `127.0.0.1:9000`（这个写法在本地起了隔离网络实测过）：

```bash
docker run --rm --network container:"$(docker compose -f infra/docker-compose-wsl.yml ps -q rustfs)" \
  -e AWS_ACCESS_KEY_ID='<AccessKey>' -e AWS_SECRET_ACCESS_KEY='<SecretKey>' \
  -e AWS_DEFAULT_REGION=us-east-1 -e AWS_EC2_METADATA_DISABLED=true \
  amazon/aws-cli --endpoint-url http://127.0.0.1:9000 s3api create-bucket --bucket pushbox
```

`deploy-wsl.sh` 的 `bucket` 子命令就是上面这条。判据是 `mc ls` / `head-bucket` 的退出码，别看 `/healthz`；
CI 的服务端 job（`.github/workflows/ci.yml`）里同一动作是自动做的。跟别的系统共用一个桶可以，
但 PushBox 只认自己那套对象键。

## 🔧 常用命令

主路径那一个容器（`docker rm` 不会带走 named volume，配置、图片与日志都在；别用 `docker rm -v`）：

```bash
docker logs -f pushbox
docker restart pushbox
docker exec pushbox curl -s http://127.0.0.1:7404/healthz
docker volume ls | grep pushbox          # pushbox_data 那一个卷

# 升级：取新镜像 → 删容器 → 用同一条 docker run 再起一次（配置在卷里，安装页不会再出现）
docker pull docker.io/iamplusdev/push-box:latest
docker rm -f pushbox

# 重走一遍安装：删掉卷里的配置文件，重启后回到安装页
docker exec pushbox rm /app/data/config/pushbox.json && docker restart pushbox
```

compose 那一套：

```bash
# 查看日志 / 重启 / 升级
docker compose logs -f pushbox-server
docker compose restart
docker compose pull && docker compose up -d

# 备份数据库（拓扑 B；口令走 -e 传进容器环境，不写进命令行——命令行在宿主 ps 里可见。
# $PB_DB_PASSWORD 是 .env 里喂 mysql 镜像的那个值，与 pushbox.json 的 database.password 同值）
docker compose exec -T -e MYSQL_PWD="$PB_DB_PASSWORD" mysql \
  mysqldump -u pushbox --single-transaction --quick pushbox > backup_$(date +%Y%m%d).sql

# 停止并清理
docker compose down -v  # -v 会删除数据卷——配置、图片、日志一起没，谨慎使用！
```

### 明文配置与备份

`pushbox.json` 明文存着库口令、桶 AK/SK、管理台口令与加密口令，**这个文件（或整个 `/app/data` 卷）
必须跟着数据库一起备份**：库副本（`app_state.runtime_config_v1`）能让安装页找回配置，但卷没了、
库也没了时什么都没有；**加密口令丢了等于图片全丢**（KEK 不可轮换，旧封装钥解不开）。

`infra/backup/backup.sh` 是独立工具，它有自己的一套输入环境变量——**这些 `PB_*` 是脚本自己的入参，
不是服务端读的环境变量**，值可以从 `pushbox.json` 里抄：

| 变量 | 用途 |
|------|------|
| `AGE_RECIPIENT` | 必填；age 公钥或 ssh 公钥（改用 gpg 见脚本尾部说明） |
| `PB_DB_PASSWORD` | 必填；mysqldump 用，即 `database.password` |
| `MYSQL_HOST` / `MYSQL_PORT` | 默认 `127.0.0.1` / `3306`，即 `database.host` / `database.port` |
| `CONFIG_FILE` | `pushbox.json` 的路径；不给就试 `CONFIG_CONTAINER` |
| `CONFIG_CONTAINER` | 从容器里 `cat` 配置，默认 `pushbox-pushbox-server-1`（compose 拼的是 `<项目名>-<服务名>-<序号>`，换过 `name:` 就对不上） |
| `MEDIA_DIR` | 本地存储时指媒体目录（named volume 用 `docker volume inspect` 现查挂载点，指它下面的 `media/`） |
| `RUSTFS_DATA_DIR` | 拓扑 B：本机 RustFS 数据卷目录 |
| `PB_S3_ENDPOINT` / `PB_S3_ACCESS_KEY` / `PB_S3_SECRET_KEY` / `PB_S3_BUCKET` | 拓扑 A：远端桶走 `mc mirror` 时用，即 `storage.endpoint` / `accessKey` / `secretKey` / `bucket` |
| `BACKUP_DIR` | 可选；产物目录，默认脚本旁 `out/<UTC 时间戳>` |

卷里的两个路径一次查出来（卷名先 `docker volume ls | grep pushbox` 认一次，见「本地存储」那节）：

```bash
vol="$(docker volume inspect <卷名> -f '{{.Mountpoint}}')"
CONFIG_FILE="$vol/config/pushbox.json" MEDIA_DIR="$vol/media" ./infra/backup/backup.sh
```

产物四份：`pushbox-*.sql.gz.age`（库）、`config-*.json.age`（配置，含加密口令）、
`rustfs-*.tar.age` 或 `media-*.tar.age`（对象/图片）。**跑完看一眼清单里有没有 `config-*` 那一份**：
两个 `CONFIG_*` 都没给、docker 又不在时脚本只打一条 `⚠️` 就继续跑完，退出码仍是 0——cron 只看退出码，
这一份会静默漏掉，而它恰好是"库恢复成功、图片全部解不开"的那个原因。

库内是明文（加密只覆盖对象字节），所以产物必须 age/gpg 加密后才出机器。

## 🆘 故障排查

### 容器启动后立即退出

```bash
# 查看详细错误（主路径用 docker logs pushbox）
docker compose logs pushbox-server | tail -50

# entrypoint 只剩一条判据，它的报错自己就带修法：
# ❌ /app/data 不可写（绑到宿主目录时属主通常是 root，而容器进程是 uid 10001）
#    → 改用 named volume，或 sudo chown -R 10001:10001 <你挂给 /app/data 的那个宿主目录>
#
# 配置类的错不再让容器退出：它们在安装页上就当场报出来了，落不了盘。
```

### 打开 7404 看到的还是安装页

说明配置文件不在进程的工作目录下。容器里它固定在 `/app/data/config/pushbox.json`；
如果 `/app/data` 挂的是宿主目录而属主不对，写入会失败（安装页会把「配置写不进去」那句原话回给你）。
装完一次之后安装页就不再出现——它只在配置文件不存在时启动。

### Web 管理台 403 / 429

```bash
# 先分清是"没开"还是"口令错"：admin.password 留空时管理台整个关闭，一律回 403「管理台未启用」，
# 那是合法状态，客户端收发照旧。口令就是安装页里填的那一个，忘了就去卷里看：
docker exec pushbox cat /app/data/config/pushbox.json   # 里面有 admin.password 明文

# 要改口令：编辑卷里的 pushbox.json 再 docker restart pushbox，
# 或删掉配置文件回安装页、用「从库里找回上一次的配置」捞回来改。
# 429 = 同一来源 IP 连错口令到阈值后被锁（默认 5 次 / 5 分钟），响应里的 hint 会写还要等多久。
# 这不是故障，是限速在起作用；等一下或换一个来源 IP。锁定计数在进程内存里，重启清零。
# 注意 admin.jwtKey 是服务端自动生成回写的，不用管；手工换掉它会让所有已登录会话当场失效——
# 换登录口令不会，这正是两把钥拆开的原因。
```

### 健康检查 db=down

```bash
# db=down 是 /healthz 真去借了一条连接、那条连接没起来。先在容器里看一眼（宿主打过去是 404，见「验收」）：
docker compose exec pushbox-server curl -s http://127.0.0.1:7404/healthz

# 再往下就只能是 Java 那侧的日志，第一条异常把原因写全了：
docker compose logs pushbox-server | grep -iE 'HikariPool|Access denied|Communications link|to database' | head
#   Access denied for user 'pushbox'@'<来源 IP>'  → 口令不对，或用户没建成 'pushbox'@'%'（写成 localhost 时，
#                                                    另一个容器连过来的来源就不是 localhost，口令全对也照样 1045）
#   Access denied for user 'pushbox'@'%' to database '<库名>' → 库名对不上，或那个用户没有这个库的权限。
#                                                    MySQL 8 在这种配法下报的是 access denied，不是 "Unknown database"
#   Communications link failure                    → 地址或端口不可达。安装页的「测试连接」按钮能先把
#                                                    "口令对不对、地址通不通"单独判清楚，改配置不用重启整个流程
# 那句 `using password: ***` 里的 *** 是我们自己的日志脱敏把 YES/NO 一起遮了（§13），不是口令。
```

**不要在容器里现装 mysql 客户端**：容器跑的是 uid 10001，`apt-get update` 直接 `Permission denied`，
要装得 `docker exec -u root`，而装进可写层的东西 `docker rm` 就没了。上面那两条（`/healthz` 的 `db` 字段 +
Hikari 的第一条异常）已经把"口令错 / 地址错 / 库名错"分开了；真要手工敲 SQL，去库所在那台机器上敲。

改配置的办法就是上面那条：编辑 `/app/data/config/pushbox.json` 再 `docker restart`，
或者删掉它回安装页重填。

## ⚙️ 换端口（改宿主侧，别改容器内）

容器内固定 7404，写死在 `application.yml`、`Caddyfile` 上游、compose 的 `ports` 与 `healthcheck` 四处，
改它要四处一起动——所以别改。要换对外端口：

# 主路径：-p 的左侧

#   PB_HTTP_PORT=8080

## 🔐 HTTPS 配置（可选）

本项目 Caddy 只监听 80 端口做 HTTP 反代，**不管理 SSL 证书**。如需 HTTPS，请在前面挂 Nginx / Traefik 等做 TLS 终止。

### Nginx 反向代理示例

```nginx
server {
    listen 443 ssl http2;
    server_name pushbox.example.com;

    ssl_certificate     /etc/nginx/ssl/pushbox.crt;
    ssl_certificate_key /etc/nginx/ssl/pushbox.key;

    location / {
        proxy_pass http://127.0.0.1:80;
        proxy_http_version 1.1;
        proxy_set_header Upgrade $http_upgrade;
        proxy_set_header Connection "upgrade";
        proxy_set_header Host $host;
        proxy_set_header X-Real-IP $remote_addr;
        proxy_set_header X-Forwarded-For $proxy_add_x_forwarded_for;
        proxy_set_header X-Forwarded-Proto $scheme;
        proxy_read_timeout 300s;
        proxy_send_timeout 300s;
    }
}
```

**客户端配置：**
- Android/Windows 服务端地址填 `https://pushbox.example.com`

### 内网/Tailscale 场景

直接使用 HTTP，无需 HTTPS：
- 客户端地址：`http://IP:端口` 或 `http://域名`
