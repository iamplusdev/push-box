## 前置条件

| 组件 | 版本要求 | 用途 |
|------|----------|------|
| JDK | 21（推荐 21.0.8） | 编译 `core/` 与 `server/` |
| Maven | 3.6+ | 构建 Java 模块 |
| Node.js | 18+ | 运行探针脚本与网站 |
| Android SDK | API 34 | 编译 Android 客户端 |
| Gradle | 8.x（由 wrapper 提供） | 构建 Android |
| .NET SDK | 8.0 | 编译 Windows 客户端 |
| MySQL | 8.0（`ngram_token_size=2`） | 服务端数据库 |
| S3 兼容存储 | RustFS / MinIO | 图片转存桶（**本机开发可不装**，dev 默认落本地文件） |

### 环境变量

所有凭据只走环境变量，值写在 `deploy/env/local.env`（已 gitignore，模板 `deploy/env/local.env.example`）。本机起步**只必填一项**：

```bash
export PB_DB_PASSWORD=你的数据库密码      # 唯一的硬必填
# 库地址写在 application-dev.yml 里（jdbc:mysql://127.0.0.1:3306/pushbox），要换库才给 PB_DB_URL
```

`PB_STORAGE_TYPE` 在 dev 默认 `local`，图片落 `./data/media`，所以**不需要任何桶就能起一个能收消息的服务端**。要走对象存储才加 `PB_S3_ENDPOINT` / `PB_S3_ACCESS_KEY` / `PB_S3_SECRET_KEY`（开 `sse-c` 再追加 `PB_S3_MASTER_PASSPHRASE` 或 `PB_S3_MASTER_KEY`，二选一），并把 `PB_STORAGE_TYPE=s3` 显式写上。`DevCredentialsGuard` 按这次真实的存储类型点名缺的是哪几个键——跑 local 时报错里不会出现 `PB_S3_ENDPOINT` 这种用不到的项。

模板里每一项都带 `export`：这文件是被 `source` 进当前 shell 的，少了 `export` 只得到一组 bash 变量，而 JVM 与 `@EnabledIfEnvironmentVariable` 那批用例读的是进程环境——现象是服务端报"没配口令"、集成测试整批静默跳过，两个都长得像别的地方的 bug。

**另一件空转的事**：`application-dev.yml` 只有 `PB_DB_PASSWORD` / `PB_STORAGE_TYPE` / `PB_STORAGE_LOCAL_PATH` / `PB_S3_*` / `PB_ADMIN_SECRET` 是占位符，库地址、库用户、`object-encrypt`、`admin.jwt-secret`、端口都写死在 yml 里。往 `local.env` 里加 `PB_SERVER_PORT` 想换端口不会有任何变化（要换就传 `--server.port=8081`），这类键在模板里逐个标注了"dev 不读"。

**铁律**：配置文件里出现明文口令就算事故。

### Gradle 依赖仓库

`android/settings.gradle.kts` 默认只用官方源（`google()` / `mavenCentral()` / `gradlePluginPortal()`），
CI 与境外使用者都走这一份口径。在国内开发机上拉依赖慢的话，在 `android/local.properties`（已 gitignore，
与签名配置同一个文件）加一行开镜像：

```properties
pb.maven.cnMirror=true
```

不要为了自己方便把镜像地址写回 `settings.gradle.kts` 的默认路径：2026-10-20 `build-apk.yml` 在 runner 上红
了一整轮，就是因为镜像排在 `pluginManagement` 最前面而 GitHub 的机器打它整片返 502，插件被报成"哪个仓库都
没有"——本机在墙内看不见这个 502，所以本地一直是绿的。

## 目录结构

```
core/       Java 加密与协议库（X25519 / Ed25519 / AES-GCM 帧通道 / canonical 签名 / 帧 DTO / 测试向量）
server/     Spring Boot 服务端：入站 API、设备与频道、WS 下发、抓取转存、搜索、治理接口
android/    Android 客户端（Kotlin + Compose），Gradle 工程，:pbcore 直接编译 ../core 的同一份源码
windows/    Windows 客户端（.NET 8 + WPF），独立解决方案；协议对齐由 testvectors/vectors.json 校验
deploy/     探针、Dockerfile、compose、Caddyfile、自签 CA、备份脚本、Prometheus/Grafana
docs/       软件设计方案（唯一权威文档）、Windows 开发环境安装教程
site/       对外介绍的官网 + 文档站源码（零构建，index.html 是首页；线上地址 https://iamplusdev.github.io/push-box/）
testvectors/ 由 core 的单测产出，供 Windows 侧对字节，必须能检出与 diff
```

`core/` 与 `server/` 是同一个 Maven reactor（根 `pom.xml` 聚合）；`android/` 与 `windows/` 各有独立的构建体系。三端**不是三份协议实现**：Java 与 Kotlin 共享同一份 `core` 源码，C# 那一侧靠 `testvectors/vectors.json` 逐字节对账。

`vectors.json` 是**按 key 排序**写出的（`CryptoVectorsTest` 里显式开了 Jackson 的 `ORDER_MAP_ENTRIES_BY_KEYS`）。别去掉这一行：文件里那些嵌套块用 `Map.of()` 构造，它的迭代顺序 JDK 不保证、跨进程还会变，不排序就是"每次跑完 core 测试，向量文件换一套 key 顺序"——内容一模一样却报出满屏 diff，下一版真改了某个字节没人分得清。

## 编译与运行

### 1. 构建服务端

```bash
# 确保 JAVA_HOME 指向 JDK 21
JAVA_HOME=/path/to/jdk-21 mvn -B -DskipTests package

# 起服务端（dev 继承 base yml 的 7404；脚本自己 source local.env）
bash deploy/run-dev.sh
```

### 2. 构建 Android

```bash
cd android
./gradlew :app:assembleDebug
```

APK 输出在 `android/app/build/outputs/apk/debug/`。

### 3. 构建 Windows

```bash
cd windows
dotnet build -c Release
```

可执行文件在 `windows/PushBox.Windows/bin/Release/net8.0-windows/`。

### 4. 验收探针

```bash
node deploy/probe/p0-e2e.mjs
```

探针会模拟一个"软件版 Android 设备"，逐字节复刻握手、签名、帧加密与补拉。判据是**末行 `N/N` 且 0 失败**，别把某个具体条数当判据（用例只许涨，但脚本里带序号的标签比 23 多）。

## 测试矩阵

| 跑法 | 判什么 |
|------|--------|
| `JAVA_HOME=… mvn -B -pl core,server test`（先 `set -a && . deploy/env/local.env && set +a`） | 服务端与加密库（**319/319** = core 43 + server 276）；碰库/碰桶的 114 条挂 `PB_S3_ACCESS_KEY` 门控，缺凭据时是 **205 执行 + 114 跳过**而退出码仍为 0——总数变小先查环境变量，别改测试 |
| `node deploy/probe/p0-e2e.mjs` | 端到端协议 + 幂等、断线补齐、隔离、吊销、截断、图文同帧、补拉循环、接入过滤（末行 **`N/N`、0 失败**） |
| `node deploy/probe/rustfs-capability.mjs` | 桶能力回归（多部分、生命周期、SSE-C 三点） |
| `cd android && ./gradlew :app:assembleDebug` | Android 编译（真机行为靠模拟器/手机走查） |
| `dotnet test windows/PushBox.sln` | C# 协议向量 + 全部客户端逻辑，判据是断言不是人眼（**554/554**，去掉会话筛选用例后） |
| `dotnet run --project windows/PushBox.LiveCheck -- http://127.0.0.1:8081` | PC 端十二条真服务端判据（延迟、签名、字节接口、DELETE、接入过滤） |

## 开发工作流

### 改协议字段

改了协议字段要**三处同步**：

1. `core/src/main/java/cn/iamplus/pushbox/core/Frames.java`
2. `android/app/src/main/java/cn/iamplus/pushbox/net/Wire.kt`
3. `deploy/probe/p0-e2e.mjs`

漏改会被探针判红，这是好事。

### 调试服务端

服务端日志用 `%pbmsg`/`pbex` 转换器兜底，`application.yml` 刻意不写 `logging.pattern.*`。**正文不进日志**是设计如此。

启动时加 `--debug` 可看更详细的 WS 握手过程。

### 调试 Android

Android 使用 Compose，建议在 Android Studio 中打开 `android/` 目录。`:pbcore` 模块直接引用 `../core`，改 Java 代码后重新 `:app:assembleDebug` 即可。

### 调试 Windows

Windows 使用 WPF，建议在 Rider 或 Visual Studio 中打开 `windows/PushBox.sln`。`PushBox.LiveCheck` 项目用于真服务端体检，跑在自起的 8081 端口上。

## 常见坑

### JDK 版本

机器默认 `JAVA_HOME` 常是 JDK 8，必须显式覆盖到 jdk-21，否则报成片乱码语法错。

### 端口占用

用户自己手动起的那个实例占 7404；代理与真服务体检另起 8081，跑完只杀自己叫起来的 PID。

### 路径大小写

NTFS 大小写不敏感但会记住工具写进去的新大小写，写错就等于悄悄改名。编辑文件时注意照磁盘原样。

### 证书校验

绝不绕过证书校验。找不到 `ServerCertificateCustomValidationCallback`、`DangerousAcceptAnyServerCertificate`、`ServicePointManager` 的钩子是设计如此，不是遗漏。自签场景只有一种接法：把 CA 装进信任根。

## 发布流程

三条发布链互相独立：服务端、Android、Windows 各有自己的版本号与标签前缀（`server-v*` / `android-v*` /
`windows-v*`），**只改一端就只打那一端的标签**，另外两条流水线不会被触发；旧的 `v*` 标签仍然保留，
一次发三端（旧标签只带一个号，所以三端版本号都得先写成这个 `X.Y.Z`）。打标签才会发版：服务端推 Docker
镜像，两端发布 GitHub Release（那份 Release 就是「检查更新 / 启动时自动检查更新」读取的更新源）——版本号
抬了没打标签，应用内是查不到的。

### 通用步骤

1. 写版本号，只动这一端：
   ```bash
   bash scripts/set-version.sh --only=server 1.2.0    # pom / web-admin / 两份 compose / site 徽章
   bash scripts/set-version.sh --only=android 1.2.0   # versionName + versionCode
   bash scripts/set-version.sh --only=windows 1.2.0   # csproj + Inno
   ```
   三端一起发时去掉 `--only=…`。脚本只接受严格 `X.Y.Z`，`versionCode = major*10000 + minor*100 + patch`
   且必须大于上一版；解析不出就报错退出、不改任何文件。
2. 提交改动，跑 `bash scripts/release-verify.sh` 到零 FAIL（它按端检查各自的版本自洽，不要求三端同号）。
3. 打对应标签并推送：
   ```bash
   git tag server-v1.2.0   && git push origin server-v1.2.0
   git tag android-v1.2.0  && git push origin android-v1.2.0
   git tag windows-v1.2.0  && git push origin windows-v1.2.0
   ```
   三端一起发才用 `v1.2.0`（三个 workflow 都认这个旧前缀）。客户端 tag 里的版本建议与 `versionName` /
   `<Version>` 相同；服务端 tag **必须**与 `pom.xml` 相同，否则版本闸门会在构建前拦红。

### 各端本地构建（不经过 CI）

1. 服务端：`mvn -B package -DskipTests`，打 Docker 镜像或直接部署 jar。
2. Android：`./gradlew :app:assembleRelease`，用正式 keystore 签名。
3. Windows：`dotnet publish -c Release -r win-x64 --self-contained`，再用 Inno Setup 打包安装包。

### 客户端更新检查的取数方式

分端发布后每个平台各占一个 Release，所以两端读的是 `releases?per_page=30` 列表，按资产名
（`pushbox-release-*.apk` / `PushBox-Setup-*-win-x64.exe`）挑出自己那条，再从 tag 里去掉
`android-v` / `windows-v` / `v` 前缀得到版本号。**不要改回 `/releases/latest`**：那个接口只返回最后发的
那个 Release，另一平台会读到别人的 tag 或看不到自己的新版本，而且不会报错。
